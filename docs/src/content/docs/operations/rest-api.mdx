---
title: REST API
description: "Inspect and control workers, queues, jobs and workflows over HTTP."
---

VarMQ ships an HTTP handler that lets you look at your workers, queues, jobs and workflows, and control them from outside the process. It serves JSON. It lists only workers that have a name. `/queues` lists their in-memory queues, and shared storage bound to a worker in this process.

:::caution
The REST API has no authentication. Anyone who can reach it can stop your workers and change their concurrency. They can read job payloads, results and errors, cancel jobs, and pause a shared queue for every process. They can also cancel a workflow, which runs its undo jobs by default. Put authentication and rate limits in front of it, with middleware or a reverse proxy. Listening on loopback alone does not stop a browser on the same host, so check the `Host` header or require a token.
:::

## Routes at a glance

The paths follow the prefix you give to `Handler`, for example `/varmq`.

| Method | Path | Does |
|---|---|---|
| `GET` | `/health` | returns `{"status":"ok"}` |
| `GET` | `/workers` | lists every registered worker, with a summary |
| `GET` | `/workers/{name}` | returns one worker, with its counters |
| `PATCH` | `/workers/{name}/actions/{action}` | pauses, resumes, restarts, starts or stops a worker |
| `PATCH` | `/workers/{name}/config/concurrency/{number}` | changes the worker's concurrency limit |
| `GET` | `/queues` | lists every known queue, with its counts and totals |
| `PATCH` | `/queues/{id}/actions/{action}` | pauses or resumes a queue |
| `GET` | `/queues/{id}/jobs?state=…` | lists a queue's jobs in one state |
| `GET` | `/queues/{id}/jobs/{jobId}` | returns one job |
| `PATCH` | `/queues/{id}/jobs/{jobId}/actions/cancel` | cancels one job |
| `GET` | `/workflows` | lists workflows, newest first |
| `GET` | `/workflows/{id}` | returns one workflow, with its tasks |
| `GET` | `/workflow-counts` | counts the workflows of each store, by state |
| `PATCH` | `/workflows/{id}/actions/cancel` | cancels a workflow |

## Mounting it

[`Handler`](https://pkg.go.dev/github.com/goptics/varmq#Handler) takes a path prefix and returns an [`http.Handler`](https://pkg.go.dev/net/http#Handler). It strips the prefix from each request before it looks for a route. Mount it on a mux with the prefix in the pattern, with a trailing slash:

```go
mux := http.NewServeMux()
mux.Handle("/varmq/", varmq.Handler("/varmq"))
http.ListenAndServe("127.0.0.1:8080", mux)
```

You can also pass the handler to `ListenAndServe` itself, as `examples/api-control` does with `varmq.Handler("/api")`. Then the routes start at `/api`.

[`NewServerMux`](https://pkg.go.dev/github.com/goptics/varmq#NewServerMux) returns the same routes as an [`*http.ServeMux`](https://pkg.go.dev/net/http#ServeMux) with no prefix, for mounting them yourself. `Handler` is `NewServerMux` behind that prefix, with one addition. It sets the [instance header](#which-instance-answered) on every response. This includes the 404 and 405 replies that the mux generates for itself. With `NewServerMux` alone, those two replies do not carry the header.

The program below starts two named workers and an unnamed one, adds jobs to them, and serves the API under `/varmq`.

```go collapse={1-12}
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"

	"github.com/goptics/varmq"
)

func main() {
	// A string argument names the worker.
	emails := varmq.NewWorker(
		func(j varmq.Job[string]) {
			time.Sleep(2 * time.Second)
		},
		"email-sender",
		2,
	)
	emailQueue := emails.BindQueue()

	// WithName does the same.
	images := varmq.NewWorker(
		func(j varmq.Job[int]) {
			time.Sleep(500 * time.Millisecond)
		},
		varmq.WithName("image-processor"),
		varmq.WithConcurrency(4),
	)
	imageQueue := images.BindQueue()

	// This worker has no name, so the API does not list it.
	varmq.NewWorker(func(j varmq.Job[int]) {}).BindQueue()

	go func() {
		for i := range 20 {
			emailQueue.Add(fmt.Sprintf("mail-%d", i))
			imageQueue.Add(i)
		}
	}()

	mux := http.NewServeMux()
	mux.Handle("/varmq/", varmq.Handler("/varmq"))

	// The API has no authentication, so listen on loopback only.
	log.Println("listening on 127.0.0.1:8080")
	log.Fatal(http.ListenAndServe("127.0.0.1:8080", mux))
}
```

### Run locally

1. Make a module, save the program as `main.go` and add VarMQ:

   ```bash
   mkdir rest-demo && cd rest-demo
   go mod init rest-demo
   go get github.com/goptics/varmq
   ```

2. Run it with `go run .`.
3. In another terminal, ask for the workers:

   ```bash
   curl localhost:8080/varmq/health
   curl localhost:8080/varmq/workers
   curl localhost:8080/varmq/workers/email-sender
   ```

   The first prints `{"status":"ok"}`. The second prints a JSON array with two workers, `email-sender` and `image-processor`, and not the unnamed one. The third prints one worker with its counters, for example:

   ```json
   {"name":"email-sender","status":"Running","concurrency":2,"num_processing":2,"num_pending":14,"num_idle_workers":0,"queue_ids":["memory:host-a:fifo:1"],"strategy":"priority","sources":[{"queue_id":"memory:host-a:fifo:1","kind":"queue"}],"metrics":{"completed":4,"successful":4,"failed":0}}
   ```

   The numbers depend on when you ask. The middle of the queue ID is this process's [instance ID](#which-instance-answered), the host name by default.

4. Control a worker:

   ```bash
   curl -i -X PATCH localhost:8080/varmq/workers/email-sender/actions/pause
   curl localhost:8080/varmq/workers/email-sender
   curl -X PATCH localhost:8080/varmq/workers/email-sender/actions/resume
   curl -i -X PATCH localhost:8080/varmq/workers/email-sender/config/concurrency/4
   ```

   The first prints a `200 OK` with no body. While a job is running, the next call shows the worker as `Pausing`, and later `Paused`, as [`Pause`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Pause) does. Run `resume` once it reads `Paused`: on a worker that is still `Pausing`, it is refused (see [the status codes](#responses)). The last call changes the limit to 4.

The repository's `examples/api-control` runs four named workers with a steady supply of jobs. [vartop](/operations/vartop/) is a separate web dashboard and command line that reads and controls this API across every process of a service. The example's last comment suggests pointing it at `http://localhost:8080/api`.

## Which workers it serves

The API serves the workers in [`WorkerRegistry`](https://pkg.go.dev/github.com/goptics/varmq#WorkerRegistry), a package-level `sync.Map` from name to worker.

- **Only a named worker is registered.** [`WithName`](https://pkg.go.dev/github.com/goptics/varmq#WithName) and a plain string argument to [`NewWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewWorker) both give a worker a name. A worker with no name is not in the registry and cannot be reached.
- **A worker is registered when it starts.** A worker created with [`WithAutoRun(false)`](https://pkg.go.dev/github.com/goptics/varmq#WithAutoRun) is not in the registry until you call [`Start`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Start).
- **A name holds one worker.** When a second worker with the same name starts, it replaces the first in the registry. The API then reaches the second.
- **A stopped worker stays for a while.** After it reaches `Stopped`, the [`WithStoppedRetention`](https://pkg.go.dev/github.com/goptics/varmq#WithStoppedRetention) time starts. The default is one minute. When that time has passed, the worker is removed from the registry, unless it was started again. [Lifecycle](/concepts/lifecycle/#withstoppedretention) has the details.
- **The order of `/workers` is not defined.** It follows the order the map yields entries in.

You can read the registry yourself. `varmq.WorkerRegistry.Load("email-sender")` returns the worker as an `any`. A type assertion to [`varmq.Worker`](https://pkg.go.dev/github.com/goptics/varmq#Worker) gives you its methods. You can then build your own routes on it.

## Routes

[Routes at a glance](#routes-at-a-glance) has the table of routes.

On a worker route, the `{action}` is one of `pause`, `resume`, `restart`, `start` and `stop`. Each calls the worker method of the same name, which [lifecycle](/concepts/lifecycle/#moving-between-states) describes. Two behaviours follow from that:

- **`pause` and `stop` return immediately.** A worker that is running jobs reads `Pausing` or `Stopping` until they end. Read the worker again to see when it has changed.
- **`restart` waits.** [`Restart`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Restart) stops the worker, waits until it has stopped, and starts it. The request is answered after that, so it can take as long as the running jobs do.

The concurrency route calls [`TunePool`](https://pkg.go.dev/github.com/goptics/varmq#Worker.TunePool) with the number. A number below 1 becomes the CPU count. [Concurrency](/guides/concurrency/#changing-the-limit-with-tunepool) covers what a change does to jobs already running.

## What a worker looks like

`/workers` returns a JSON array of these. `/workers/{name}` returns one, with `strategy`, `sources` and `metrics` added:

| Field | From |
|---|---|
| `name` | the worker's [`Name`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Name) |
| `status` | [`Status`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Status): `Initiated`, `Idle`, `Running`, `Pausing`, `Paused`, `Stopping` or `Stopped` |
| `concurrency` | [`NumConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumConcurrency), the limit |
| `num_processing` | [`NumProcessing`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumProcessing) |
| `num_pending` | [`NumPending`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumPending) |
| `num_idle_workers` | [`NumIdleWorkers`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumIdleWorkers) |
| `queue_ids` | the IDs of the queues the worker takes from, sorted. They are the IDs that [`/queues`](#queues-and-jobs) uses. The list is empty when no queue has an ID. |
| `strategy` (`/workers/{name}` only) | the worker's [`WithStrategy`](https://pkg.go.dev/github.com/goptics/varmq#WithStrategy): `priority`, `round_robin`, `max_len` or `min_len` |
| `sources` (`/workers/{name}` only) | each bound queue or topic subscription, in the order the worker's strategy ranks them. See [the source fields](#source-fields). |
| `metrics.completed`, `successful`, `failed` (`/workers/{name}` only) | the three counters of [`Metrics()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Metrics) |

### Source fields

Each entry of `sources` has three fields:

- **`queue_id`** is the queue's `/queues` ID. It is `""` for a topic subscription, or for storage with no queue ID.
- **`kind`** is `queue` or `topic`.
- **`priority`** comes from [`WithQueuePriority`](https://pkg.go.dev/github.com/goptics/varmq#WithQueuePriority) or [`WithTopicPriority`](https://pkg.go.dev/github.com/goptics/varmq#WithTopicPriority). It is absent when not set, or set to `math.MaxInt`, which ranks the same.

The list is sorted by `priority`, lowest first, then the sources with none. Sources with the same priority keep the order you bound them in.

[Waiting](/guides/waiting/) covers what `NumPending` and `NumProcessing` count, and [Metrics](/guides/metrics/) covers the three counters. For a worker on shared storage, see [the overview](/persistence/overview/#metrics).

## Queues and jobs

`/queues` lists every queue that can report its state. These are the in-memory queues of named workers. They also include shared storage, such as redisq or sqliteq, bound to a worker in this process. A queue that several workers share is listed once. Each entry looks like this:

```json
{"id":"memory:host-a:fifo:1","counts":{"pending":18,"processing":2,"completed":0,"failed":0},"totals":{"submitted":20,"completed":0,"failed":0},"paused":false}
```

| Field | What it is |
|---|---|
| `id` | the queue ID. An in-memory queue's ID is `memory:` followed by the instance ID, the queue kind and a number. |
| `counts` | `pending` and `processing` are the jobs in those states now. `completed` and `failed` are the records the storage still keeps. An in-memory queue keeps them only with `WithEndedJobs`. |
| `totals` | the jobs the queue received (`submitted`), and how many of them completed or failed since it started counting. |
| `paused`, `paused_at` | whether the queue is [paused](/guides/queues/#pausing-a-queue), and since when, in Unix milliseconds. |
| `error` | the storage's error, when it could not report its state. The other fields are then absent. |

In Go, an entry is a [`QueueStats`](https://pkg.go.dev/github.com/goptics/varmq#QueueStats), with [`JobCounts`](https://pkg.go.dev/github.com/goptics/varmq#JobCounts) and [`JobTotals`](https://pkg.go.dev/github.com/goptics/varmq#JobTotals). A job record is a [`JobRecord`](https://pkg.go.dev/github.com/goptics/varmq#JobRecord), with one [`JobError`](https://pkg.go.dev/github.com/goptics/varmq#JobError) per failed attempt. Its `state` is a [`JobState`](https://pkg.go.dev/github.com/goptics/varmq#JobState): [`JobPending`](https://pkg.go.dev/github.com/goptics/varmq#JobPending), [`JobProcessing`](https://pkg.go.dev/github.com/goptics/varmq#JobProcessing), [`JobCompleted`](https://pkg.go.dev/github.com/goptics/varmq#JobCompleted), [`JobFailed`](https://pkg.go.dev/github.com/goptics/varmq#JobFailed) or [`JobCancelled`](https://pkg.go.dev/github.com/goptics/varmq#JobCancelled). A workflow task can also be [`JobWaiting`](https://pkg.go.dev/github.com/goptics/varmq#JobWaiting).

**Pausing a queue.** `PATCH /queues/{id}/actions/pause` and `…/resume` pause and resume the queue. They answer `200` with the queue's entry. On shared storage, the pause stops every process that takes from the queue, and it survives a restart.

**Listing jobs.** `GET /queues/{id}/jobs` needs a `state`: `pending`, `processing`, `completed`, `failed` or `cancelled`. `offset` starts at 0. `limit` is 50 by default and at most 1000. Each record has the job's `id`, `state`, `payload`, timestamps, `attempts` and `errors`. A list leaves out a job's result and gives its size as `result_size`.

**Reading one job.** `GET /queues/{id}/jobs/{jobId}` returns one record, with its result. The storage must be able to read a job by its ID. The in-memory queues can. redisq and sqliteq cannot yet, so they answer `501`.

**Cancelling a job.** `PATCH /queues/{id}/jobs/{jobId}/actions/cancel` answers `202` with no body. It works like [`Cancel`](/concepts/jobs/#cancelling-a-job) on the job's handle.

- **An in-memory queue finds a job with an ID while the job waits in the queue or runs.** It answers `404` for any other ID.
- **Shared storage cannot tell a waiting job from an unknown ID.** So it answers `202` for any ID with no ended record. It marks the ID cancelled for 24 hours, or until a new job is added with that ID through `WithJobId`.
- **A job whose ended record is still kept** answers `409`.
- **A waiting workflow task on shared storage** answers `202` but still runs. To stop it, cancel its workflow. A running task's `Context()` is cancelled, as for any job.

An in-memory queue keeps no ended jobs by default. Pass [`WithEndedJobs`](https://pkg.go.dev/github.com/goptics/varmq#WithEndedJobs) when you bind it, so the `completed`, `failed` and `cancelled` lists have records. The in-memory job routes work only for a named worker, after you build the handler.

## Workflows

The workflow routes read the [workflow](/guides/workflows/) stores this process knows. These are the in-memory stores you made with [`NewWorkflowStore`](https://pkg.go.dev/github.com/goptics/varmq#NewWorkflowStore), and every store an adapter registered, such as `redisq.NewWorkflowStore`. A process that only submits workflows, and runs no worker, lists and cancels them too. So protect the handler there as well.

- **`GET /workflows`** lists the workflows of every store, newest first. `state` filters them, for example `running` or `failed`. `offset` is at most 10000, and `limit` is 50 by default and at most 1000.
- **`GET /workflows/{id}`** returns one workflow, with the state of each task. A task also shows when it went to its queue (`enqueued_at`), when a worker started it (`started_at`) and when it ended (`finished_at`), in Unix milliseconds. A store that does not keep these times leaves them out.
- **`GET /workflow-counts`** counts the workflows by state. It returns one entry for each store, and one entry for all in-memory stores of the process. An entry with `shared: true` is the same on every instance that uses the store, so count it one time. An entry without `counts` comes from a store that cannot count, or whose count failed. Show no counts then. The reply is 503 only when no store counted and one failed. The `store` value is an opaque ID, a short hash of the store's scope. It is not a secret. For a file store, the hash includes the host name, so the same path on two hosts gives two IDs.
- **`PATCH /workflows/{id}/actions/cancel`** cancels the workflow and answers `200` with its record. Add `?undo=false` to skip the undo steps. The API cannot turn on undo steps that the workflow turned off: `?undo=true` answers 400.

## Responses

Every response with a body sets `Content-Type: application/json`. A successful worker action, and a job cancel, have no body. An error is a JSON object with one field, `error`.

| Status | When | Example | Body |
|---|---|---|---|
| 200 | the request worked | any read, a worker action, a queue pause, a workflow cancel | JSON for a read, a queue pause or a workflow cancel. Empty for a worker action or a concurrency change. |
| 202 | a job cancel was accepted | `PATCH …/jobs/job-1/actions/cancel` | empty |
| 400 | the action is unknown, or a number or query value is not valid | `actions/jump`, `concurrency/four`, `jobs` with no `state` | for example `{"error":"unknown action"}` |
| 404 | no registered worker, queue, job or workflow has that name or ID | a worker with no name, or one removed from the registry | for example `{"error":"worker not found"}` |
| 409 | the call conflicts with the current state | `start` on a running worker, a cancel of a job that ended | the error's message, for example `{"error":"worker is already running"}` |
| 500 | a worker call returned any other error, or a job read failed | `resume` on a `Pausing` worker, `pause` on a stopped one | the error's message, for example `{"error":"worker is stopped"}` |
| 501 | the storage does not support the route | a pause on storage with no pause, a one-job read on redisq | the error's message |
| 503 | the storage failed | Redis is down during a pause, a cancel or a workflow read | the error's message |

The 409 and 500 rows of the worker routes follow the error the worker returns.

- **409:** [`ErrRunningWorker`](https://pkg.go.dev/github.com/goptics/varmq#ErrRunningWorker), [`ErrNotRunningWorker`](https://pkg.go.dev/github.com/goptics/varmq#ErrNotRunningWorker) and [`ErrSameConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#ErrSameConcurrency). So `start` on a running worker, or a concurrency change to the same number, is a 409.
- **500:** [`ErrWorkerPausing`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerPausing), [`ErrWorkerPaused`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerPaused), [`ErrWorkerStopping`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerStopping) and [`ErrWorkerStopped`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerStopped). So `resume` on a `Pausing` worker is a 500 with `worker is pausing`.

[Errors](/guides/errors/#returned-by-calls-you-make) lists which call returns which error. A workflow route also answers 409 when two stores hold the same workflow ID.

Two replies do not come from the routes. A path the mux does not know gets a plain-text `404 page not found`. A known path with the wrong method gets a plain-text `405 Method Not Allowed` with an `Allow` header.

## Which instance answered

[`InstanceHeader`](https://pkg.go.dev/github.com/goptics/varmq#InstanceHeader) is the name of a response header, `X-Varmq-Instance`. Its value is [`InstanceID`](https://pkg.go.dev/github.com/goptics/varmq#InstanceID). When several instances sit behind one URL, such as a load balancer, the header tells you which process answered.

`InstanceID` is a package variable. It starts as the host name, which on Kubernetes is the pod name, or as an empty string if the host name is not available. Set it before you start serving when several instances share a host:

```go
varmq.InstanceID = "worker-a"
```

Every response from the routes carries the header, whether you use `Handler` or `NewServerMux`. As described above, only `Handler` also adds it to the mux's own 404 and 405 replies.
