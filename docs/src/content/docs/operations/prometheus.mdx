VarMQ imports no metrics library. A worker exposes what Prometheus needs as plain methods: how many jobs are running and waiting, and three counters of what has happened. You wrap those methods in collectors from the [Prometheus Go client](https://github.com/prometheus/client_golang). Its [`GaugeFunc`](https://pkg.go.dev/github.com/prometheus/client_golang/prometheus#GaugeFunc) and [`CounterFunc`](https://pkg.go.dev/github.com/prometheus/client_golang/prometheus#CounterFunc) call a function each time Prometheus scrapes, so nothing of yours has to poll the worker.

A longer version of the program below is in [`examples/prometheus`](https://github.com/goptics/varmq/tree/main/examples/prometheus).

## A worker with metrics

The program below runs a worker with concurrency 10, registers seven collectors for it, and serves them at `/metrics`. It adds 1000 jobs that each take 100 milliseconds.

```go collapse={1-14}
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"

	"github.com/goptics/varmq"
	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
	worker := varmq.NewWorker(
		func(j varmq.Job[string]) {
			time.Sleep(100 * time.Millisecond)
		},
		varmq.WithConcurrency(10),
	)
	queue := worker.BindQueue()

	registerMetrics(worker, "foo_worker")
	http.Handle("/metrics", promhttp.Handler())

	go func() {
		for i := range 1000 {
			queue.Add(fmt.Sprintf("task-%d", i))
		}
	}()

	log.Println("metrics on http://localhost:8080/metrics")
	log.Fatal(http.ListenAndServe(":8080", nil))
}

// Each collector calls its function on every scrape, so a value is read when
// Prometheus asks for it.
func registerMetrics(w varmq.Worker, namespace string) {
	gauge := func(name, help string, read func() int) {
		prometheus.MustRegister(prometheus.NewGaugeFunc(
			prometheus.GaugeOpts{Namespace: namespace, Name: name, Help: help},
			func() float64 { return float64(read()) },
		))
	}
	counter := func(name, help string, read func() uint64) {
		prometheus.MustRegister(prometheus.NewCounterFunc(
			prometheus.CounterOpts{Namespace: namespace, Name: name, Help: help},
			func() float64 { return float64(read()) },
		))
	}

	m := w.Metrics()

	gauge("workers_processing", "Jobs being processed right now", w.NumProcessing)
	gauge("workers_concurrency", "Maximum number of jobs processed at once", w.NumConcurrency)
	gauge("workers_idle", "Idle goroutines in the pool", w.NumIdleWorkers)
	gauge("jobs_waiting", "Jobs not started yet; can read high while batches run", w.NumPending)

	counter("completed_total", "Jobs whose function has returned", m.Completed)
	counter("successful_total", "Jobs that returned without an error or a panic", m.Successful)
	counter("failed_total", "Jobs that returned an error or panicked", m.Failed)
}
```

### Run locally

1. Make a module, save the program as `main.go` and add the dependencies:

   ```bash
   mkdir prometheus-demo && cd prometheus-demo
   go mod init prometheus-demo
   go get github.com/goptics/varmq github.com/prometheus/client_golang
   ```

2. Run it with `go run .`.
3. In another terminal, read the metrics while the jobs run:

   ```bash
   curl -s localhost:8080/metrics | grep "^foo_worker"
   ```

   The output looks like this a moment after the start. The numbers depend on when you ask:

   ```
   foo_worker_completed_total 190
   foo_worker_failed_total 0
   foo_worker_successful_total 190
   foo_worker_jobs_waiting 800
   foo_worker_workers_concurrency 10
   foo_worker_workers_idle 0
   foo_worker_workers_processing 10
   ```

4. Ask again after about fifteen seconds. All 1000 jobs have completed, `jobs_waiting` and `workers_processing` read 0, and `workers_idle` reads 1.

Leave out `grep` to see the `# HELP` and `# TYPE` lines too, and the Go runtime and process metrics. [`promhttp.Handler()`](https://pkg.go.dev/github.com/prometheus/client_golang/prometheus/promhttp#Handler) serves the default registry, which has those as well.

## The metrics

With the namespace `foo_worker`, each name starts with `foo_worker_`. The scene below replays the scrape of the program above. Move the clock, press a metric to read what it is, and see the PromQL for it. The numbers follow a real run of the program: 1000 jobs, 100 milliseconds each, 10 at a time.

| Name | Type | From | What it is |
|---|---|---|---|
| `workers_processing` | gauge | [`NumProcessing`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumProcessing) | jobs being processed right now |
| `workers_concurrency` | gauge | [`NumConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumConcurrency) | the concurrency limit |
| `workers_idle` | gauge | [`NumIdleWorkers`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumIdleWorkers) | idle goroutines in the pool |
| `jobs_waiting` | gauge | [`NumPending`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumPending) | jobs that have not started. While a batch runs it can read high: see [waiting](/guides/waiting/#numpending-and-numprocessing) |
| `completed_total` | counter | [`Completed`](https://pkg.go.dev/github.com/goptics/varmq#Metrics.Completed) | jobs whose function has returned |
| `successful_total` | counter | [`Successful`](https://pkg.go.dev/github.com/goptics/varmq#Metrics.Successful) | jobs that returned without an error or a panic |
| `failed_total` | counter | [`Failed`](https://pkg.go.dev/github.com/goptics/varmq#Metrics.Failed) | jobs that returned an error or panicked |

The three counters are the three of [`Metrics()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Metrics). A worker does not count the jobs its queues receive. Each queue counts them: read `totals.submitted` from [`GET /queues`](/operations/rest-api/#queues-and-jobs). [Metrics](/guides/metrics/) explains what each counts. [Waiting](/guides/waiting/) explains what `NumPending` and `NumProcessing` count.

## Queries to start with

These use the namespace `foo_worker`. Change it to the namespace you pass to each collector.

| Question | PromQL |
|---|---|
| How many jobs finish each second? | `rate(foo_worker_completed_total[5m])` |
| What share of finished jobs fail? | `rate(foo_worker_failed_total[5m]) / rate(foo_worker_completed_total[5m])` |
| How full is the pool? (1 means every slot runs a job) | `foo_worker_workers_processing / foo_worker_workers_concurrency` |
| How large is the backlog? | `foo_worker_jobs_waiting` |
| Does the backlog grow? | `deriv(foo_worker_jobs_waiting[5m]) > 0` |

The failure share is `NaN` while no job finishes. The pool can read above 1 just after [`TunePool`](https://pkg.go.dev/github.com/goptics/varmq#Worker.TunePool) lowers the limit, while the jobs already running finish. The last row is true while jobs arrive faster than they finish. On shared storage, each process counts only the jobs it ran. [The overview](/persistence/overview/#metrics) says more.

## What to watch for

- **The reads are not one snapshot.** A scrape reads seven values at slightly different moments, and a job can finish between two of them. A set read while jobs run can be off by a few. [Metrics](/guides/metrics/#reading-them) says more.
- **The counters start at zero when the worker is created.** They are totals. Use `rate()` or `increase()` in Prometheus to see how many jobs ran in a period. A restart of the process zeroes them, and Prometheus functions such as `rate()` read a drop as a counter reset.
- **[`Reset`](https://pkg.go.dev/github.com/goptics/varmq#Metrics.Reset) makes a counter fall.** It zeroes the three counters, and Prometheus reads that as a reset, like a restart. Do not call it on a worker you export unless you want that.
- **One namespace for each worker.** `MustRegister` panics when a collector with the same metric name is registered twice, with `duplicate metrics collector registration attempted`. Register each worker under its own namespace.
- **A worker on shared storage asks its storage.** `NumPending` reads the length from Redis or SQLite. So every scrape makes that call. For the counters of such a worker, see [the overview](/persistence/overview/#metrics).

## Scraping it

Point Prometheus at the address the program listens on. A minimal scrape configuration is:

```yaml
scrape_configs:
  - job_name: varmq
    static_configs:
      - targets: ["localhost:8080"]
```

Prometheus scrapes `/metrics` by default, which is where the program serves them. If you serve VarMQ's [REST API](/operations/rest-api/) as well, it can sit on the same server: mount it with `http.Handle("/varmq/", varmq.Handler("/varmq"))` next to the metrics route. The REST API lists only named workers, so give the worker a name. The REST API returns the same worker numbers as JSON, which suits a dashboard, and Prometheus suits history and alerts.
