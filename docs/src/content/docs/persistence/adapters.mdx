A storage adapter is a type that implements some of VarMQ's queue interfaces. redisq and sqliteq are adapters. A type of your own can also be one. VarMQ decides what a queue can do by the interfaces its value implements. It checks them with a type assertion when you bind the queue or add a job. If an interface is not implemented, its behaviour is off. This is not an error. This page lists them all, from [`IBaseQueue`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue) to the small job interfaces. They are all in the `varmq` package.

For using redisq or sqliteq, read [Redis](/persistence/redis/) and [SQLite](/persistence/sqlite/) instead. [The overview](/persistence/overview/) covers what shared storage does.

The map below shows how the interfaces fit together. Press a part to say that your type has it, and the boxes that combine parts switch on. Press a box to read what it adds, what the worker calls on it and when. The start-from buttons load redisq and sqliteq as the table at the end of the page describes them.

## What you pass and what you get

| You call | Storage must implement | You get |
|---|---|---|
| [`WithQueue`](https://pkg.go.dev/github.com/goptics/varmq#IWorkerBinder.WithQueue) | [`IQueue`](https://pkg.go.dev/github.com/goptics/varmq#IQueue) | [`Queue[T]`](https://pkg.go.dev/github.com/goptics/varmq#Queue). With [`IAcknowledgeable`](#iacknowledgeable) too, VarMQ treats the queue as shared storage. |
| [`WithPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IWorkerBinder.WithPriorityQueue) | [`IPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPriorityQueue) | [`PriorityQueue[T]`](https://pkg.go.dev/github.com/goptics/varmq#PriorityQueue), shared in the same way |
| [`NewQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewQueue), [`NewErrQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewErrQueue) or [`NewResultQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewResultQueue), no worker | [`IPersistentQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPersistentQueue) | [`ProducerQueue[T, J]`](https://pkg.go.dev/github.com/goptics/varmq#ProducerQueue), whose `Add` returns a job handle |
| [`NewPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewPriorityQueue), [`NewErrPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewErrPriorityQueue) or [`NewResultPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#NewResultPriorityQueue), no worker | [`IPersistentPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPersistentPriorityQueue) | [`ProducerPriorityQueue[T, J]`](https://pkg.go.dev/github.com/goptics/varmq#ProducerPriorityQueue) |

Queues store values of type `any`. An in-memory queue, and one you bind with `WithQueue` or `WithPriorityQueue`, stores the job values VarMQ creates. [`Add`](https://pkg.go.dev/github.com/goptics/varmq#Queue.Add) on shared storage encodes the job as JSON and passes the `[]byte` to [`Enqueue`](https://pkg.go.dev/github.com/goptics/varmq#IQueue.Enqueue). What the storage gives back has to be that `[]byte`, or a job value. Anything else is reported as [`ErrFailedToCastJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrFailedToCastJob), and bytes that do not decode are [`ErrParseJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrParseJob).

What the worker assumes of any queue:

- **It is safe to call from several goroutines.** Callers add jobs from their own goroutines. The worker's event loop reads. Every job's goroutine acknowledges when it ends.
- **A read that finds nothing returns `false` for `ok`.** The worker checks [`Len`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Len) before it reads. If a read then finds nothing, for example because another consumer took the job meanwhile, the worker reports [`ErrFailedToDequeue`](https://pkg.go.dev/github.com/goptics/varmq#ErrFailedToDequeue) on [`Errs()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Errs) and to the handler.
- **Optional interfaces are found on the value you pass.** A wrapper can hold the adapter behind an interface such as `IQueue`. Such a wrapper hides [`IBatchAcknowledgeable`](https://pkg.go.dev/github.com/goptics/varmq#IBatchAcknowledgeable) and [`CapacitySetter`](https://pkg.go.dev/github.com/goptics/varmq#CapacitySetter). The behaviour they add is then off.

## The queue interfaces

### `IBaseQueue`

The root of every queue. Every queue you give to VarMQ has these five methods:

| Method | The worker calls it |
|---|---|
| [`Len() int`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Len) | Whenever it decides whether there is work: before it pulls a job, for [`NumPending`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumPending), for [`Wait`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Wait), and for the `MaxLen` and `MinLen` [strategies](/guides/strategies/). On shared storage each call is a call to the storage. |
| [`Dequeue() (any, bool)`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Dequeue) | Once for each job it takes from a queue that does not acknowledge. It does not call it on a queue that is [`IAcknowledgeable`](#iacknowledgeable), which it reads with [`DequeueWithAckId`](https://pkg.go.dev/github.com/goptics/varmq#IAcknowledgeable.DequeueWithAckId). |
| [`Values() []any`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Values) | Only when you call [`Purge`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Purge) on the handle. VarMQ reads what is in the queue and clears it. Then it closes every value that implements [`io.Closer`](https://pkg.go.dev/io#Closer), so a purged job reads `Closed`. |
| [`Purge()`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Purge) | When you call `Purge` on the handle, as above. |
| [`Close() error`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Close) | When you call `Close` on the handle. |

On shared storage, `Purge` cannot close the jobs it drops, because they live in the storage. Instead, the handle stops waiting on the jobs it added, including running ones: their `Err` returns [`ErrDetached`](https://pkg.go.dev/github.com/goptics/varmq#ErrDetached).

### `IQueue` and `IPriorityQueue`

[`IQueue`](https://pkg.go.dev/github.com/goptics/varmq#IQueue) adds [`Enqueue(item any) bool`](https://pkg.go.dev/github.com/goptics/varmq#IQueue.Enqueue) and [`EnqueueOnce(item any, id string) bool`](https://pkg.go.dev/github.com/goptics/varmq#IQueue.EnqueueOnce) to `IBaseQueue`. [`IPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPriorityQueue) adds [`Enqueue(item any, priority int) bool`](https://pkg.go.dev/github.com/goptics/varmq#IPriorityQueue.Enqueue) and [`EnqueueOnce(item any, priority int, id string) bool`](https://pkg.go.dev/github.com/goptics/varmq#IPriorityQueue.EnqueueOnce).

The handle's `Add` calls `Enqueue` once for each job, or [`EnqueueOnce`](#enqueueonce) when the job has an ID. `true` means the item is stored, or, on shared storage, that a job with the same ID already was. `false` makes `Add` return `false`.

The priority is the number the caller passed to `Add`. VarMQ does not order the queue. The worker takes whatever `Dequeue` returns next. So a priority queue has to give out the lowest number first itself. For the built-in queues, and for redisq and sqliteq, a lower number comes first.

### `IAcknowledgeable`

The interface that makes a queue persistent. It has three methods:

| Method | The worker calls it |
|---|---|
| [`DequeueWithAckId() (any, bool, string)`](https://pkg.go.dev/github.com/goptics/varmq#IAcknowledgeable.DequeueWithAckId) | Once for each job it takes, when a slot is free and `Len` is above 0. It returns the item, whether there was one, and an acknowledgement ID. |
| [`Acknowledge(ackID string) bool`](https://pkg.go.dev/github.com/goptics/varmq#IAcknowledgeable.Acknowledge) | Once for each job that succeeded, with the ID it was given, when the job's function has returned and the worker closes the job. It returns whether the storage accepted it. |
| [`Reject(ackID string, reason string) bool`](https://pkg.go.dev/github.com/goptics/varmq#IAcknowledgeable.Reject) | In place of `Acknowledge`, for a job whose function returned an error or panicked. `reason` is the error text. The storage removes the job and does not requeue it. It returns whether the storage accepted it. |

The worker keeps the ID on the job and passes it back unchanged. An empty ID means there is nothing to acknowledge, and the worker calls neither method for that job. `Acknowledge` or `Reject` returning `false` makes the worker report [`ErrAcknowledgeJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrAcknowledgeJob). The storage decides what happens to an item that is taken and not acknowledged. It can give it out again after a timeout, at the next start, or never. So the delivery guarantee is the adapter's.

A worker takes one job per call. A job it took stays unacknowledged until it has run. If the worker held several, other consumers could not get them. The exception is the batch interface below.

### `IBatchAcknowledgeable`

An optional addition to `IAcknowledgeable`. [`IBatchAcknowledgeable`](https://pkg.go.dev/github.com/goptics/varmq#IBatchAcknowledgeable) has one more method, [`DequeueBatchWithAckIds(items []any, ackIDs []string) (n, remaining int, err error)`](https://pkg.go.dev/github.com/goptics/varmq#IBatchAcknowledgeable.DequeueBatchWithAckIds), for storage that can take many jobs in one call.

When the storage implements it and is the worker's only bound source, the worker reads it differently:

- **One call per wake-up.** The worker counts its free slots and calls `DequeueBatchWithAckIds` with buffers of that size, at most 64. It does not call `Len` between jobs.
- **Every job a call took starts.** The worker starts each job as it decodes it. It keeps none back, even if [`TunePool`](https://pkg.go.dev/github.com/goptics/varmq#Worker.TunePool) lowers the concurrency limit during the call. It also keeps none back if a pause or a stop arrives. The jobs are unacknowledged. If the worker kept them, a visibility timeout could give them to another consumer. A lower limit applies from the next call.
- **`n` is how many it moved.** The storage moves items into `items[:n]` and `ackIDs[:n]`, each item under its own ID, in one atomic step. It moves no more than the smaller of the two slice lengths. `n` is 0 with a `nil` error when the storage is empty.
- **`remaining` is the length after the move.** It may be a lower bound when the storage caps its count. It has to be above 0 whenever items remain, because the worker uses it to decide whether to call again.
- **A short call normally means the storage is empty.** The worker then stops pulling until something signals work. Storage may also return a short call with `remaining` above 0. For example, it can do this for items it gives back from an earlier failed call. The worker then pulls again.
- **`err` is a failure.** The worker reports it and pulls again on the next sign of work.
- **An item that does not decode is reported and not acknowledged.** The worker sends the error and leaves the item to the storage.

Signals matter because the worker does not probe the storage on its own after a short or failed call. Storage without `Subscribe` is signalled by the process's own `Add` calls. Also, a worker that last saw the storage empty checks `Len` once a second. It does this while the worker is active and this is its only source. Storage with [`Subscribe`](https://pkg.go.dev/github.com/goptics/varmq#ISubscribable.Subscribe) is signalled by it. An adapter can implement both [`ISubscribable`](https://pkg.go.dev/github.com/goptics/varmq#ISubscribable) and this interface. Such an adapter has to send `"enqueued"` for items that no `Enqueue` announced:

- items a visibility timeout put back
- items another client added
- items left after a failed call

Sending it about once a second while items wait does that.

With another source bound as well, the worker reads this storage one job at a time through `DequeueWithAckId`, and checks `Len` before each read.

Binding a storage that implements it also signals the worker, because the storage may already hold jobs and no `Add` will announce them. So the [start-up trap](/persistence/overview/#starting-a-worker-on-a-non-empty-queue) does not arise with it.

### `EnqueueOnce`

`IQueue` and `IPriorityQueue` both have [`EnqueueOnce`](https://pkg.go.dev/github.com/goptics/varmq#IQueue.EnqueueOnce). It stores the item unless an item with the same ID is already stored. A storage that does not check IDs can call its `Enqueue` from it.

Earlier releases had it in the optional `IDedupQueue` and `IDedupPriorityQueue` interfaces. Those are removed, so move the method onto your queue type as it is.

`Add` calls it, in place of `Enqueue`, for a job with an ID you gave, with [`WithJobId`](https://pkg.go.dev/github.com/goptics/varmq#WithJobId) or [`Item.ID`](https://pkg.go.dev/github.com/goptics/varmq#Item). A generated ID does not count. [Job IDs](/guides/job-ids/#persistent-and-distributed-queues) says how long shared storage keeps an ID, and what `Add` returns for a repeat.

A producer made with `NewQueue` has no worker. The worker's [`WithJobIdGenerator`](https://pkg.go.dev/github.com/goptics/varmq#WithJobIdGenerator) does not reach it. It uses an ID you pass with `WithJobId`, or the one [`DefaultJobIdGenerator`](https://pkg.go.dev/github.com/goptics/varmq#DefaultJobIdGenerator) sets. With neither, it makes a random ID when the storage reports outcomes or cancels jobs.

### `IPersistentQueue` and `IPersistentPriorityQueue`

[`IPersistentQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPersistentQueue) is `IQueue` plus `IAcknowledgeable`, and [`IPersistentPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPersistentPriorityQueue) is `IPriorityQueue` plus `IAcknowledgeable`. They add no methods. `NewQueue` and `NewPriorityQueue` ask for them, and `WithQueue` and `WithPriorityQueue` detect them.

Binding one wraps it so that `Add` writes JSON and the worker reads with `DequeueWithAckId`, or with `DequeueBatchWithAckIds` when the storage implements it. The worker takes one job per free slot. [`Pause`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Pause) and [`Stop`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Stop) do not park a job it already took.

### `ISubscribable`

[`ISubscribable`](https://pkg.go.dev/github.com/goptics/varmq#ISubscribable) has one method, [`Subscribe(func(action string))`](https://pkg.go.dev/github.com/goptics/varmq#ISubscribable.Subscribe). It is what makes a queue distributed.

`WithQueue` and `WithPriorityQueue` call `Subscribe` once, while binding, when shared storage (`IAcknowledgeable`) implements it. They pass the worker's handler. The adapter calls the handler with a string for each event. The worker acts on one: `"enqueued"` makes it wake to pull. Any other action is ignored, so an adapter may send others. The handler runs on whichever goroutine the adapter calls it from, and it does not block. The interface has no way to unsubscribe, so the handler stays until the adapter stops calling it. `NewQueue` does not call `Subscribe`, because it has no worker.

### `IDistributedQueue` and `IDistributedPriorityQueue`

[`IDistributedQueue`](https://pkg.go.dev/github.com/goptics/varmq#IDistributedQueue) is `IPersistentQueue` plus `ISubscribable`, and [`IDistributedPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IDistributedPriorityQueue) is `IPersistentPriorityQueue` plus `ISubscribable`. They add no methods of their own.

### `CapacitySetter`

[`CapacitySetter`](https://pkg.go.dev/github.com/goptics/varmq#CapacitySetter) is optional and has one method, [`SetCapacity(cap int)`](https://pkg.go.dev/github.com/goptics/varmq#CapacitySetter.SetCapacity). VarMQ calls it when it creates a queue handle, with the number from [`WithQueueCapacity`](https://pkg.go.dev/github.com/goptics/varmq#WithQueueCapacity). It calls it even when you passed no capacity, with 0, so an implementation has to read a number below 1 as no limit. After that, it is the storage's job to refuse `Enqueue` when it is full.

Without it, [`IsFull`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.IsFull) on the handle compares `Len` with the number, and `Add` is not refused. [Queues](/guides/queues/#capacity) covers capacity.

### Optional interfaces

Each interface below adds one feature. VarMQ checks for it on the storage value, and turns the feature off when it is missing. Most come from the `contract` module, which an adapter can import without VarMQ. The `varmq` package has an alias for each.

| Interface | Methods | Adds |
|---|---|---|
| [`IPurgeValuesQueue`](https://pkg.go.dev/github.com/goptics/varmq#IPurgeValuesQueue) | `PurgeValues() []any` | `Purge` empties the queue in one atomic step. |
| [`QueuePauser`](https://pkg.go.dev/github.com/goptics/varmq#QueuePauser) | `Pause() error`, `Resume() error`, `Paused() bool` | a [queue pause](/guides/queues/#pausing-a-queue) kept in the storage. Without it, `Pause` returns `ErrPauseUnsupported`. |
| [`PauseNotifier`](https://pkg.go.dev/github.com/goptics/varmq#PauseNotifier) | `OnPauseChange(fn func(paused bool)) (cancel func())` | a worker starts at once after a `Resume` in another process. |
| [`OutcomeWatcher`](https://pkg.go.dev/github.com/goptics/varmq#OutcomeWatcher) | `WatchOutcome(id string, fn func(JobOutcome)) (cancel func())` | job handles learn how a job ended. Without it, `Err` returns `ErrDetached`. |
| [`ResultAcknowledgeable`](https://pkg.go.dev/github.com/goptics/varmq#ResultAcknowledgeable) | `AcknowledgeResult(ackID string, result []byte) bool` | a result worker's result reaches the handle that added the job. |
| [`JobCanceller`](https://pkg.go.dev/github.com/goptics/varmq#JobCanceller) | `CancelJob(id string) error` | [`Cancel`](/concepts/jobs/#cancelling-a-job) and the REST cancel route. Without it, `Cancel` returns `ErrCancelUnsupported`. |
| [`CancelNotifier`](https://pkg.go.dev/github.com/goptics/varmq#CancelNotifier) | `OnCancel(fn func(jobID string)) (stop func())` | a cancel from any process reaches the job while it runs. |
| [`CancelAcknowledgeable`](https://pkg.go.dev/github.com/goptics/varmq#CancelAcknowledgeable) | `AcknowledgeCancelled(ackID, reason string) bool` | a cancelled job is recorded as cancelled. Without it, VarMQ calls `Reject`. |
| [`QueueInspector`](https://pkg.go.dev/github.com/goptics/varmq#QueueInspector) | `QueueID()`, `QueueStats(ctx)`, `Jobs(ctx, state, offset, limit)` | the queue's counts and job records, for [`GET /queues`](/operations/rest-api/#queues-and-jobs). |
| [`JobReader`](https://pkg.go.dev/github.com/goptics/varmq#JobReader) | `Job(ctx, id) (JobRecord, error)` | the REST route that reads one job. Without it, the route answers 501. |
| [`Scoped`](https://pkg.go.dev/github.com/goptics/varmq#Scoped) | `ScopeID()` | [workflow](/guides/workflows/) tasks on this storage, with `QueueInspector`. A worker finds the workflow store by this scope. |
| [`WorkflowInspector`](https://pkg.go.dev/github.com/goptics/varmq#WorkflowInspector) | `Workflows(ctx, state, offset, limit)`, `ScopeID()` | on a workflow store: the store's workflows in [`GET /workflows`](/operations/rest-api/#workflows). |
| [`WorkflowCounter`](https://pkg.go.dev/github.com/goptics/varmq#WorkflowCounter) | `WorkflowCounts(ctx) (map[WorkflowState]int64, error)` | on a workflow store: the store's numbers in [`GET /workflow-counts`](/operations/rest-api/#workflows). Without it, the store's entry has no counts. |
| [`HostLocal`](https://pkg.go.dev/github.com/goptics/varmq#HostLocal) | `HostLocal()` | on a workflow store in a file on the host: the host name goes into the store's ID in `GET /workflow-counts`, so the same path on two hosts counts as two stores. |
| [`InstanceRegistry`](https://pkg.go.dev/github.com/goptics/varmq#InstanceRegistry) | `ReportInstance`, `RemoveInstance`, `Instances` | a record of each process, its workers and their queues, for dashboards. VarMQ supplies the record. |

The types these methods use are in the `contract` module too.

- **Outcomes:** `WatchOutcome` reports a [`JobOutcome`](https://pkg.go.dev/github.com/goptics/varmq#JobOutcome).
- **Instances:** a record is an [`InstanceRecord`](https://pkg.go.dev/github.com/goptics/varmq#InstanceRecord), with one [`InstanceWorker`](https://pkg.go.dev/github.com/goptics/varmq#InstanceWorker) per worker.
- **Scopes:** a queue and a workflow store with the same `ScopeID` belong together. The adapter's store constructor registers the store with `contract.RegisterWorkflowStore`, one store per scope in a process. VarMQ finds it with `contract.LookupWorkflowStore`. The store must be a pointer, and its `Close` must call `contract.UnregisterWorkflowStore`.
- **Workflows:** `Submit` takes a [`WorkflowPlan`](https://pkg.go.dev/github.com/goptics/varmq#WorkflowPlan), with a [`TaskPlan`](https://pkg.go.dev/github.com/goptics/varmq#TaskPlan) per task and an [`UndoPlan`](https://pkg.go.dev/github.com/goptics/varmq#UndoPlan) per undo job. The store's `FinishTask` takes the queue ID, the acknowledgement ID and a [`TaskEnd`](https://pkg.go.dev/github.com/goptics/varmq#TaskEnd). Its [`Outcome`](https://pkg.go.dev/github.com/goptics/varmq#Outcome) is [`OutcomeCompleted`](https://pkg.go.dev/github.com/goptics/varmq#OutcomeCompleted), [`OutcomeFailed`](https://pkg.go.dev/github.com/goptics/varmq#OutcomeFailed) or [`OutcomeCancelled`](https://pkg.go.dev/github.com/goptics/varmq#OutcomeCancelled).
- **Listing workflows:** a store that implements [`WorkflowKeyLister`](https://pkg.go.dev/github.com/goptics/varmq#WorkflowKeyLister) lists [`WorkflowKey`](https://pkg.go.dev/github.com/goptics/varmq#WorkflowKey) values. Then `GET /workflows` reads a full record only for the workflows on its page.
- **Task times:** a store can fill `EnqueuedAt`, `StartedAt` and `FinishedAt` of a [`TaskRecord`](https://pkg.go.dev/github.com/goptics/varmq#TaskRecord), in Unix milliseconds. It sets `StartedAt` when its `Runnable` answers true. A store that does not keep the times leaves them at 0.

## The handle and the job interfaces

The rest of the interfaces are not for adapters to implement. They describe what VarMQ gives you. They are listed here because they sit next to the queue interfaces in the API reference.

### [`IExternalBaseQueue`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue)

[`IExternalBaseQueue`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue) is what every queue handle has: `Len`, `IsFull`, `Purge`, `Close`, `Pause`, `Resume` and `IsPaused`. The handles a worker binds also have `Worker()`, and a producer handle from `NewQueue` does not. VarMQ implements it around your storage. `Len`, `Purge` and `Close` reach the `IBaseQueue` methods above, and `IsFull` reads `Len`.

### Job interfaces

The job interfaces are small pieces that the job and group handles are built from. None of them is for storage to implement, because the jobs are VarMQ's own values.

| Interface | Methods | Where it appears |
|---|---|---|
| [`Identifiable`](https://pkg.go.dev/github.com/goptics/varmq#Identifiable) | [`ID() string`](https://pkg.go.dev/github.com/goptics/varmq#Identifiable.ID), empty when no ID was set | [`Job[T]`](https://pkg.go.dev/github.com/goptics/varmq#Job), the argument of the worker function, and every job handle |
| [`StatusProvider`](https://pkg.go.dev/github.com/goptics/varmq#StatusProvider) | [`IsClosed() bool`](https://pkg.go.dev/github.com/goptics/varmq#StatusProvider.IsClosed) and [`Status() string`](https://pkg.go.dev/github.com/goptics/varmq#StatusProvider.Status) | every job handle. The worker calls `IsClosed` on each job it takes from a queue and skips a closed one. |
| [`Awaitable`](https://pkg.go.dev/github.com/goptics/varmq#Awaitable) | [`Wait()`](https://pkg.go.dev/github.com/goptics/varmq#Awaitable.Wait), which blocks until the job is closed, or for a group until every job in it has ended. [`WaitContext(ctx)`](https://pkg.go.dev/github.com/goptics/varmq#Awaitable.WaitContext) also gives up when `ctx` ends. | every job handle, and the group handles |
| [`Drainer`](https://pkg.go.dev/github.com/goptics/varmq#Drainer) | [`Drain()`](https://pkg.go.dev/github.com/goptics/varmq#Drainer.Drain), which discards the results or errors a group's channel still holds. A single job has no channel, so it does nothing there. | error and result job handles, and error and result group handles |
| [`PendingTracker`](https://pkg.go.dev/github.com/goptics/varmq#PendingTracker) | [`NumPending() int`](https://pkg.go.dev/github.com/goptics/varmq#PendingTracker.NumPending), the number of pending jobs in a group | the handles [`AddAll`](https://pkg.go.dev/github.com/goptics/varmq#Queue.AddAll) returns |

The handles of shared storage have them too. In the worker function, `Job[T]` is the argument for every queue, and on shared storage its `ID()` returns the `id` stored in the JSON. [Jobs](/concepts/jobs/) and [worker types](/guides/worker-types/) cover the handles.

## What redisq and sqliteq implement

The table is for redisq v1.6.0 and sqliteq v0.4.0. [Installation](/start/installation/#versions) has the versions.

| Interface | redisq | sqliteq |
|---|---|---|
| `IBaseQueue`, `IQueue`, `IPriorityQueue`, `IAcknowledgeable` | yes | yes |
| `IPersistentQueue`, `IPersistentPriorityQueue` | yes | yes |
| `ISubscribable`, `IDistributedQueue`, `IDistributedPriorityQueue` | yes | no |
| `IBatchAcknowledgeable` | yes | yes |
| `EnqueueOnce` checks job IDs | yes | yes |
| `QueuePauser`, `PauseNotifier` | yes | yes |
| `OutcomeWatcher`, `ResultAcknowledgeable` | yes | yes |
| `JobCanceller`, `CancelNotifier`, `CancelAcknowledgeable` | yes | yes |
| `QueueInspector` | yes | yes |
| `JobReader` | no | no |
| `Scoped`, and a workflow store (`NewWorkflowStore`) | yes | yes |
| `InstanceRegistry` | yes, on its `Queues` value | no |
| `CapacitySetter`, `IPurgeValuesQueue` | no | no |
