A job has no ID unless you give it one: [`ID()`](https://pkg.go.dev/github.com/goptics/varmq#Identifiable.ID) returns an empty string. An ID names the job for your own bookkeeping. On an in-memory queue it also keeps a second job with the same ID from waiting in the queue next to the first. [Jobs](/concepts/jobs/#job-ids) introduces IDs. This page has the details.

## Giving a job an ID

There are three ways.

| How | Where | The job gets |
|---|---|---|
| [`WithJobId("job-1")`](https://pkg.go.dev/github.com/goptics/varmq#WithJobId) | an option you pass to [`Add`](https://pkg.go.dev/github.com/goptics/varmq#Queue.Add) | that ID. An empty string is ignored. |
| [`Item.ID`](https://pkg.go.dev/github.com/goptics/varmq#Item) | a field of the `Item` values you pass to [`AddAll`](https://pkg.go.dev/github.com/goptics/varmq#Queue.AddAll) | that ID with a `g:` prefix. |
| [`WithJobIdGenerator(fn)`](https://pkg.go.dev/github.com/goptics/varmq#WithJobIdGenerator) | an option you pass to the worker | whatever `fn` returns, when no ID was given. |

The generator is a `func() string`. Passing `nil` is ignored. Without a generator, a job with no ID of its own has none. [`DefaultJobIdGenerator`](https://pkg.go.dev/github.com/goptics/varmq#DefaultJobIdGenerator) sets a generator for the workers you create after the call.

A few details:

- An ID from `WithJobId` or `Item.ID` takes the place of the generated one. `Add` still calls the generator when you pass `WithJobId`, and throws its value away, so a counting generator skips a number. `AddAll` calls it only for items that have no ID.
- A generated ID on an `AddAll` item gets the `g:` prefix too.
- `Add` calls the generator on the goroutine that calls `Add`. If several goroutines add jobs, the generator has to be safe for concurrent use.

## Where you see the ID

- In the worker function, as `j.ID()` on the [`Job`](https://pkg.go.dev/github.com/goptics/varmq#Job) it receives.
- On the handle `Add` returns: `job.ID()`.
- In each [`Result`](https://pkg.go.dev/github.com/goptics/varmq#Result) that [`Results()`](https://pkg.go.dev/github.com/goptics/varmq#EnqueuedResultGroupJob.Results) delivers for an `AddAll` group on a result worker, in its [`JobId`](https://pkg.go.dev/github.com/goptics/varmq#Result) field. See [adding many jobs](/guides/adding-many/).

It is the empty string when the job has no ID.

## Deduplicating

An in-memory queue keeps at most one job per given ID in the queue. While a job with an ID is in the queue, a second `Add` with the same ID is refused: it returns a `nil` handle and `false`.

```go
queue.Add(userID, varmq.WithJobId("refresh:"+userID)) // queued
queue.Add(userID, varmq.WithJobId("refresh:"+userID)) // nil, false: one is already in the queue
```

That suits work where many callers ask for the same thing, and one waiting job is enough.

### When an ID is free

The queue holds an ID while its job is in the queue. The ID is released when a worker takes the job out of the queue, or when [`Purge`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.Purge) removes it.

A worker takes jobs out ahead of running them, and with a FIFO queue it may take several at once in a batch ([how it works](/concepts/how-it-works/#batched-dispatch)). A job in a batch, or one parked by a [pause or stop](/concepts/lifecycle/#what-happens-to-jobs), has left the queue, so it has released its ID. Its [status](/concepts/jobs/#job-status) still reads `Queued`. A duplicate `Add` is accepted at that point.

So the rule is one job per ID *in the queue*, not one live job per ID. It does not stop the same ID from running twice at once: when a worker has taken the first job, the ID is free.

Closing a job with its handle's [`Close`](https://pkg.go.dev/github.com/goptics/varmq#EnqueuedJob.Close) does not free its ID. `Close` leaves the job in the queue, so it keeps the ID until the worker reaches it or `Purge` removes it. See [closing a queued job](/concepts/jobs/#closing-a-queued-job).

### What is checked

- Only IDs you gave, with `WithJobId` or `Item.ID`. A generated ID is not checked, and two jobs with no ID are both stored.
- `AddAll` applies the same rule per item. An item whose ID is held by a job in the queue is skipped, and so is a repeat within the same slice, while the first copy is still in the queue (a running worker may already have taken it). Items get a `g:` prefix, so an item with ID `a` and an `Add` with `WithJobId("a")` do not collide.
- Every in-memory queue is checked: FIFO and priority queues, and their error and result variants.
- A queue you bind with [`WithQueue`](https://pkg.go.dev/github.com/goptics/varmq#IWorkerBinder.WithQueue) or [`WithPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IWorkerBinder.WithPriorityQueue) takes part only if it implements [`IDedupQueue`](https://pkg.go.dev/github.com/goptics/varmq#IDedupQueue) or [`IDedupPriorityQueue`](https://pkg.go.dev/github.com/goptics/varmq#IDedupPriorityQueue). Without that, the queue stores the duplicate.

`Add` also returns `false` for a full queue and for a closed one, and it does not say which of the three it was. See [queues](/guides/queues/).

### Persistent and distributed queues

Persistent and distributed queues do not work this way. Storage that implements `IDedupQueue` keeps an ID for a window of its own, and `Add` returns `true` for a repeat while the job is stored once. IDs there must be unique across everything you add, so use something like a UUID, and not a counter that restarts. The `IDedupQueue` documentation has the details.

## Try it

The program below creates a worker with concurrency 1 and [`WithAutoRun(false)`](https://pkg.go.dev/github.com/goptics/varmq#WithAutoRun), plus an ID generator. Nothing is started, so the jobs wait in the queue. That keeps the output the same on every run. On a worker that is running, the first `Add` would be taken at once and its ID released.

The output, line by line:

1. `generated: auto-1`. The first job has no `WithJobId`, so the generator named it.
2. `first refresh: true refresh`. The job got the ID `refresh`.
3. `second refresh: false - handle is nil: true`. A job with the ID `refresh` is in the queue, so `Add` refused the second one and returned no handle.
4. `group queued: 1 - Len: 3`. The `AddAll` item with ID `refresh` was accepted: it is `g:refresh`, a different ID. The queue holds three jobs: `report`, `refresh 1` and `refresh 3`.
5. After [`Start`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Start), the worker prints `running report with id "auto-1"`, then `refresh 1` with ID `refresh`, then `refresh 3` with ID `"g:refresh"`, in the order they were added. `refresh 2` never runs, because it was refused. The worker sees the prefix on the `AddAll` item.
6. `running refresh 4 with id "refresh"` and then `refresh after it ran: true`. Those jobs had left the queue, so the ID `refresh` was free to use again.
