A queue gives each job to one worker. A [`Topic`](https://pkg.go.dev/github.com/goptics/varmq#Topic) gives each payload to every worker subscribed to it. Use one when several workers must each act on the same event, such as sending an email and updating stock for the same order.

| | In-memory queue | Topic |
|---|---|---|
| Who gets a job | one worker, once | every subscribed worker, each with its own job |
| You send with | [`queue.Add(x)`](https://pkg.go.dev/github.com/goptics/varmq#Queue.Add) | [`topic.Publish(x)`](https://pkg.go.dev/github.com/goptics/varmq#Topic.Publish) |
| You get back | a job handle and a `bool` | a `bool` |

**Topics are in-memory only.** A topic lives in your process. Nothing is written to disk, and a payload is lost when the process exits.

## Creating a topic and subscribing

[`NewTopic`](https://pkg.go.dev/github.com/goptics/varmq#NewTopic) creates a topic for payloads of one type. [`WithTopic`](https://pkg.go.dev/github.com/goptics/varmq#IWorkerBinder.WithTopic) subscribes a worker to it:

<GoPlay example="topic-subscribe" />

![Two workers subscribed to one topic: each Publish stores the payload once in a shared log and wakes both workers, and each worker reads it through its own cursor and runs its own job](../../../../../assets/diagrams/varmq-topic.svg)

`WithTopic` is available on the worker that [`NewWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewWorker) returns. Error and result workers cannot subscribe: see the table in [worker types](/guides/worker-types/#which-queues-each-worker-can-bind).

`WithTopic` returns a [`Subscription`](https://pkg.go.dev/github.com/goptics/varmq#Subscription), the worker's handle on the topic. A subscription has no `Add`, because the topic is the only producer. Two calls panic: subscribing a worker to a topic it is already subscribed to, and passing a `nil` topic. A worker can subscribe again after it unsubscribes.

## Publishing

`Publish` stores the payload once and wakes every subscribed worker. Each worker then makes its own job from the payload. The payload is copied by value, so if `T` is a pointer or holds pointers, maps or slices, every subscriber shares what they point to.

`Publish` returns `true` once the payload is stored. It returns `false`, and no subscriber gets the payload, in three cases:

- no worker is subscribed, so the payload has nowhere to go;
- the topic is closed;
- the topic is full: see [capacity](#capacity).

It returns when the payload is stored, not when the jobs finish. To wait for a subscriber's jobs, wait on that subscriber's worker: [waiting](/guides/waiting/) covers how. A job made from a payload gets its ID from the subscriber's own [job ID generator](/guides/job-ids/), and a worker with no generator gives it none.

A worker receives only the payloads published after it subscribed. A payload that `Publish` refused for lack of subscribers is not kept for the next one.

## How a topic stores payloads

A topic keeps one copy of each payload in a shared in-memory log, however many workers subscribe. Each subscription reads the log at its own position, so a slow worker does not block `Publish` or the other workers. A payload is freed once every subscription has read it. In the diagram, that is why a chunk of the log stays while the slower worker's cursor is still on it.

The same rule means a subscriber that is slow, paused or stopped holds on to every payload published since it fell behind, until it catches up, purges or unsubscribes. For a worker that may stall, set a [capacity](#capacity).

## Unsubscribing

[`Unsubscribe`](https://pkg.go.dev/github.com/goptics/varmq#Subscription.Unsubscribe) on the subscription ends it. The worker gets nothing more from the topic, and the payloads it has not read yet are dropped. A job the worker has already taken from the topic is not recalled: a running job finishes, and a job waiting in a batch still runs. Calling it twice is safe. [`Close`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.Close) on the subscription does the same.

[`Purge`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.Purge) on a subscription keeps the subscription and drops the unread payloads. Unlike `Unsubscribe`, it also discards the jobs the worker has taken from the topic but not started, so a job waiting in a batch does not run. A job that is already running finishes. `Purge` does not call `Close` on the payloads. [`Len`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.Len) is the number of payloads the subscription has not read, and [`Worker()`](https://pkg.go.dev/github.com/goptics/varmq#Subscription.Worker) returns its worker.

To end every subscription at once, call [`Close`](https://pkg.go.dev/github.com/goptics/varmq#Topic.Close) on the topic. It unsubscribes all of them, and every later `Publish` returns `false`. [`NumSubscribers()`](https://pkg.go.dev/github.com/goptics/varmq#Topic.NumSubscribers) tells you how many are attached.

## Capacity

A topic has no limit unless you set one. [`WithTopicCapacity`](https://pkg.go.dev/github.com/goptics/varmq#WithTopicCapacity) bounds it when you create it:

```go
topic := varmq.NewTopic[Order](varmq.WithTopicCapacity(10_000))
```

The limit applies to the slowest subscription. Once it has that many payloads unread, `Publish` returns `false`, the way `Add` does on a full queue, and the refused payload reaches no subscriber. Room comes back as that subscription reads, purges or unsubscribes. A value below 1 means no limit.

[`IsFull()`](https://pkg.go.dev/github.com/goptics/varmq#Topic.IsFull) on the topic tells you whether it is at its capacity right now, and the answer can change straight after. On a subscription, [`IsFull()`](https://pkg.go.dev/github.com/goptics/varmq#IExternalBaseQueue.IsFull) is true when that subscription is at the capacity, which makes it the one refusing `Publish`. Act on the result of `Publish` itself, not on `IsFull`.

## Priority and strategy

A topic subscription is one more source of its worker, next to any queues bound to it. The worker's [strategy](/guides/strategies/) picks which source gives the next job. [`WithTopicPriority`](https://pkg.go.dev/github.com/goptics/varmq#WithTopicPriority) ranks the subscription the way [`WithQueuePriority`](https://pkg.go.dev/github.com/goptics/varmq#WithQueuePriority) ranks a queue: a lower number goes first, and without it the subscription ranks last.

```go
worker.WithTopic(orders, varmq.WithTopicPriority(1)) // read orders before other sources
```

With the default [`Priority`](https://pkg.go.dev/github.com/goptics/varmq#Priority) strategy, a worker with a topic subscription ranked 1 and a queue without a rank takes the payloads first. If the two have the same rank, the one bound first goes first. [Strategies](/guides/strategies/#what-priority-does-under-the-other-strategies) covers what priority does under the other three.

A worker whose only source is a topic takes payloads in batches, like a worker with one in-memory FIFO queue. With more than one source it takes one job at a time. [How it works](/concepts/how-it-works/#batched-dispatch) has both.

The program below subscribes two workers to a topic, publishes some orders, adds a third worker part-way through, and unsubscribes one. Each worker records what it received, and the program prints the records sorted, because the worker with concurrency 2 can finish its jobs in either order.

<GoPlay example="topic" />

The output, line by line:

1. `publish with no subscribers: false`. Nobody is subscribed, so `Publish` refused payload 0 and it is gone.
2. `subscribers: 3`. The `email` worker (concurrency 1) and the `stock` worker (concurrency 2) subscribed first, and the program published payloads 1 and 2. Then the `audit` worker subscribed, which makes three subscribers.
3. `after Unsubscribe, subscribers: 2`. Payload 3 went to all three workers. Then the stock subscription ended, and payload 4 went to the other two.
4. `email received [1 2 3 4]`. It was subscribed for every payload.
5. `stock received [1 2 3]`. It missed payload 4, which was published after it unsubscribed.
6. `audit received [3 4]`. It subscribed after payloads 1 and 2, so it did not see them.
7. `publish 1: true` and `publish 2: true`. The second part uses a topic with a capacity of 2 and a worker created with [`WithAutoRun(false)`](https://pkg.go.dev/github.com/goptics/varmq#WithAutoRun), which reads nothing until it starts. Two payloads fit.
8. `publish 3: false - IsFull: true`. The worker has 2 unread payloads, which is the capacity, so `Publish` refused the third.
9. `publish 3 after the worker caught up: true`. The program started the worker and waited until it was idle. That freed the room, so the same `Publish` now succeeds.
10. `slow received [1 2 3]`. The refused payload 3 was not delivered, and the second publish of 3 was.
