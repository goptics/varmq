A failure in VarMQ appears in one of three places. A few values are returned directly from calls you make. This page covers:

- where a failed job is reported;
- how to read the worker's error channel and set an error handler;
- every exported `Err` value, with the call that returns it.

[`Add`](https://pkg.go.dev/github.com/goptics/varmq#Queue.Add) has no error result. Its `bool` result is `false` when the queue did not take the job. See [queues](/guides/queues/#capacity).

## Where a failure is reported

| Where | What it gets | Which workers |
|---|---|---|
| The job's handle: [`Err()`](https://pkg.go.dev/github.com/goptics/varmq#EnqueuedErrJob.Err) or [`Result()`](https://pkg.go.dev/github.com/goptics/varmq#EnqueuedResultJob.Result) | what the function returned, or the panic | [`NewErrWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewErrWorker) and [`NewResultWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewResultWorker) |
| The worker's [`Errs()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Errs) channel | every failure the worker sees | all three |
| The error handler, set with [`WithErrHandler`](https://pkg.go.dev/github.com/goptics/varmq#WithErrHandler) | every failure the worker sees | all three |

A job's function can fail in two ways, and both are reported the same way:

- **It returns an error.** An error worker or result worker sends that error to the job's handle, to `Errs()` and to the handler. The error is the same value you returned, so [`errors.Is`](https://pkg.go.dev/errors#Is) works on it. A plain [`NewWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewWorker) function returns nothing, so it cannot fail this way.
- **It panics.** The worker recovers the panic and counts the job as failed. The panic becomes an error, which goes where a returned error goes. A plain worker has no handle to carry it, so it goes to `Errs()` and the handler only.

The error for a panic reads `panic recovered inside worker: <value>`. For an error worker it is `err-worker` instead of `worker`, and for a result worker `result-worker`. The value is formatted into the text with `%v`, so `errors.Is` cannot find the panic value inside it. [Worker types](/guides/worker-types/) shows the three handles side by side.

The worker itself can also report an error that belongs to no job function: a [storage problem](#sent-to-errs-and-the-handler) or a failed acknowledgement. Those go to `Errs()` and the handler only.

For a group of jobs added with [`AddAll`](https://pkg.go.dev/github.com/goptics/varmq#Queue.AddAll), an error group handle has its own [`Errs()`](https://pkg.go.dev/github.com/goptics/varmq#EnqueuedErrGroupJob.Errs). That one is a different channel, and it is closed once the group has ended. The worker's `Errs()` below is not. See [adding many jobs](/guides/adding-many/#reading-errors). A failure in a group job also reaches the worker's `Errs()` and the handler.

## The Errs channel

The worker's `Errs()` returns a read-only channel of `error`. Three things to know about it:

- **It holds one error.** The channel has room for a single value. When a job fails and the channel is full, the error is not put on the channel, and the worker does not wait for you. A reader that is slow, or absent, loses errors. The handler does not.
- **It is never closed.** `for err := range worker.Errs()` does not end when the worker stops. Run it in a goroutine of its own, or read with `select` and a `default`.
- **An error does not say which job it came from.** Put the job's ID, or something else that identifies the work, in the message you return.

```go
go func() {
	for err := range worker.Errs() {
		log.Println("worker error:", err)
	}
}()
```

A reader like this one drains the channel as errors arrive. If you need every error, set a handler as well. The channel can still drop an error when two errors arrive faster than the reader takes them.

## The error handler

[`WithErrHandler`](https://pkg.go.dev/github.com/goptics/varmq#WithErrHandler) sets a function that the worker calls for every error it reports. The function receives the [`Worker`](https://pkg.go.dev/github.com/goptics/varmq#Worker) and the error, so one handler can serve several workers and log the worker's [`Name()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Name). The program below names its error worker `mailer` with a string after the function and sets a handler. Job 2 returns an error and job 3 panics.

<GoPlay example="errors-handler" />

The handler runs once for each failure and prints `mailer`. Its lines come first, because the program waits for the worker to go idle before it reads the handles. Each handle then has its own outcome: `nil`, the returned error, and the panic as `panic recovered inside err-worker: boom`.

- **The handler runs for every error,** including those the full `Errs()` channel dropped.
- **It runs synchronously on the goroutine that reports the error,** and it must not block. For an error from a job, or from a failed acknowledgement, that is the goroutine that ran the job. A slow handler then delays that goroutine's next job. For an error from pulling a job off its storage, it is the worker's event loop. The event loop gives out every job, so a slow handler delays all of them.
- **Passing `nil` is ignored.** The worker keeps the handler it had.
- **The default handler does nothing.** [`DefaultErrHandler`](https://pkg.go.dev/github.com/goptics/varmq#DefaultErrHandler) changes it for the workers you create after the call. [Configuration](/guides/configuration/#the-default-functions) says how the defaults work.

The next two sections list every exported error, grouped by how you receive them. The messages are the text each one carries. Four of them are not returned from a call: the worker reports them on `Errs()` and to the handler.

### Returned by calls you make

### Sent to Errs and the handler

These four are not returned from any call. The worker reports them when it pulls a job from its storage or closes a finished job. They go to `Errs()` and to the handler, and the worker continues.

| Error | Message | Reported when |
|---|---|---|
| [`ErrFailedToDequeue`](https://pkg.go.dev/github.com/goptics/varmq#ErrFailedToDequeue) | `failed to dequeue job` | A bound queue's [`Dequeue`](https://pkg.go.dev/github.com/goptics/varmq#IBaseQueue.Dequeue) returned no job at the moment the worker pulled from it. The worker checks that a queue is not empty before it pulls. So the built-in queues rarely give it. |
| [`ErrFailedToCastJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrFailedToCastJob) | `failed to cast job` | The storage returned something that is not a job of the worker's type. The built-in queues hold jobs, so this comes from custom or shared storage. |
| [`ErrParseJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrParseJob) | `failed to parse job`, followed by the decoder's message | Shared storage returned bytes that do not decode as a job. The error wraps `ErrParseJob`, so match it with `errors.Is`. |
| [`ErrAcknowledgeJob`](https://pkg.go.dev/github.com/goptics/varmq#ErrAcknowledgeJob) | `queue failed to acknowledge job`, followed by the job and acknowledgement IDs | Shared storage refused the acknowledgement when the worker closed a job it took from it. The error wraps `ErrAcknowledgeJob`. |

Only shared storage gives out bytes to decode or jobs to acknowledge. So `ErrParseJob` and `ErrAcknowledgeJob` do not come from the built-in in-memory queues. [Persistence](/persistence/overview/) covers those queues.

A failed job on shared storage reports a [`*RemoteError`](https://pkg.go.dev/github.com/goptics/varmq#RemoteError) from `Err()` or `Result()`. It is a type, not a variable. It holds only the error text, so `errors.Is` does not find your own error values in it. Use `errors.As` to get it.

One more error has no variable. The helpers [`Func`](https://pkg.go.dev/github.com/goptics/varmq#Func), [`ErrFunc`](https://pkg.go.dev/github.com/goptics/varmq#ErrFunc) and [`ResultFunc`](https://pkg.go.dev/github.com/goptics/varmq#ResultFunc) handle a `nil` function with the error `provided function is nil`. `ErrFunc` and `ResultFunc` return it; `Func` panics with it, so the text arrives inside the panic message. It is not exported, so match it with `strings.Contains`. See [function helpers](/guides/function-helpers/#details).
