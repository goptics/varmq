A worker's concurrency is the most jobs it runs at the same time. This page covers how to set it, how to change it while the worker runs, and the options that decide how many idle goroutines the worker keeps. [How it works](/concepts/how-it-works/#the-worker-pool) shows the pool behind it.

## Setting the limit

The default is 1. A plain `int` after the worker function sets it, [`WithConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#WithConcurrency) sets it as an option, and [`DefaultConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#DefaultConcurrency) changes the default for workers created after the call:

```go
// A plain int after the function sets the limit.
varmq.NewWorker(process, 4)

// The same, as an option.
varmq.NewWorker(process, varmq.WithConcurrency(4))

// The default for workers created after this call.
varmq.DefaultConcurrency(4)
```

If you pass more than one value to a worker, the last one wins. [Worker types](/guides/worker-types/#what-follows-the-function) lists the other arguments that [`NewWorker`](https://pkg.go.dev/github.com/goptics/varmq#NewWorker) takes.

**A value below 1 means one per logical CPU.** `0` and `-1` both become [`runtime.NumCPU()`](https://pkg.go.dev/runtime#NumCPU), so the number depends on the machine. The same rule applies to `DefaultConcurrency` and to [`TunePool`](https://pkg.go.dev/github.com/goptics/varmq#Worker.TunePool), below.

## A limit, not a pool size

[`NumConcurrency()`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumConcurrency) returns the limit. It is an upper bound on the jobs running at once, not a number of goroutines the worker creates. The worker starts a goroutine when jobs are waiting and one more would clear the backlog faster than it costs to start it, up to the limit, and goroutines exit when the backlog is gone. A worker with a limit of 100 and three waiting jobs does not start 100 goroutines. [How it works](/concepts/how-it-works/#the-worker-pool) has the details.

Four methods on [`Worker`](https://pkg.go.dev/github.com/goptics/varmq#Worker) report what the pool is doing:

| Method | Returns |
|---|---|
| `NumConcurrency` | the limit |
| [`NumProcessing`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumProcessing) | the jobs running right now, counted as busy goroutines |
| [`NumPending`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumPending) | the jobs that have not started: waiting in a queue, in a batch a goroutine took, or parked by a pause or stop. While a batch runs it can read high: see [waiting](/guides/waiting/#numpending-and-numprocessing) |
| [`NumIdleWorkers`](https://pkg.go.dev/github.com/goptics/varmq#Worker.NumIdleWorkers) | the idle goroutines waiting in the pool for a job |

`NumProcessing` stays at or below the limit, except for a while after `TunePool` lowers the limit. All four are snapshots: they can change right after you read them.

## Changing the limit with TunePool

`TunePool` changes the limit of an active worker, one that is `Idle` or `Running`. It returns at once, and the new limit applies to the next job the worker hands out. A value below 1 means one per CPU, as above.

```go
if err := worker.TunePool(8); err != nil {
	log.Println("could not tune:", err)
}
```

It returns an error in two cases:

- [`ErrSameConcurrency`](https://pkg.go.dev/github.com/goptics/varmq#ErrSameConcurrency): the worker already has that limit.
- The worker is not `Idle` or `Running`. `TunePool` only works on an active worker, so it returns the error for the worker's state: [`ErrNotRunningWorker`](https://pkg.go.dev/github.com/goptics/varmq#ErrNotRunningWorker) before [`Start`](https://pkg.go.dev/github.com/goptics/varmq#Worker.Start), [`ErrWorkerPausing`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerPausing) or [`ErrWorkerPaused`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerPaused) while pausing or paused, and [`ErrWorkerStopping`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerStopping) or [`ErrWorkerStopped`](https://pkg.go.dev/github.com/goptics/varmq#ErrWorkerStopped) while stopping or stopped. The [lifecycle](/concepts/lifecycle/) page has the states.

### Raising the limit

The worker starts jobs on new goroutines as soon as it can. That covers the jobs still in a queue and the jobs you add later.

A job a goroutine has already taken into a batch stays with that goroutine, which runs its batch one job after another. This matters most at concurrency 1, where one goroutine can take up to 32 jobs at once from an in-memory FIFO queue: raising the limit does not spread out jobs it already holds. [How it works](/concepts/how-it-works/#batched-dispatch) explains batches.

### Lowering the limit

Nothing running is interrupted. The worker hands out no new batch until fewer goroutines are busy than the new limit, so `NumProcessing` can stay above `NumConcurrency` until those goroutines finish their batches. A goroutine that already holds a batch keeps running it one job after another, so jobs from batches already handed out still start after the change. The worker removes idle goroutines it no longer needs at once, unless you set an expiry duration, in which case the expiry removes them (see below).

## Idle goroutines

A worker with default settings keeps one idle goroutine in its pool. A goroutine that finishes a job stays in the pool if more jobs are waiting than idle goroutines are ready to run them, or if the pool holds fewer idle goroutines than the minimum, which is one. Otherwise it exits. Two options change this.

[`WithMinIdleWorkerRatio`](https://pkg.go.dev/github.com/goptics/varmq#WithMinIdleWorkerRatio) sets the share of the limit to keep idle, as a percentage from 1 to 100. The worker keeps `limit * percentage / 100` idle goroutines, rounded down, with a floor of one. With a limit of 4, a ratio of 50 keeps 2 and a ratio of 100 keeps 4. A value outside the range is clamped: `0` becomes 1 and anything above 100 becomes 100. The limit here is the current one, so the minimum follows a `TunePool`.

[`WithIdleWorkerExpiryDuration`](https://pkg.go.dev/github.com/goptics/varmq#WithIdleWorkerExpiryDuration) makes the pool shrink on a timer instead. With it set, a goroutine that finishes a job goes back to the pool instead of exiting. Once per duration the worker removes the goroutines that have been idle for longer than the duration, down to the minimum above. Because the check runs once per duration, a goroutine can sit idle for up to about twice the duration before it goes. Without the option there is no timer, and the pool shrinks as goroutines finish.

```go
worker := varmq.NewWorker(process, 100,
	varmq.WithMinIdleWorkerRatio(10),                   // keep 10 goroutines idle
	varmq.WithIdleWorkerExpiryDuration(30*time.Second), // drop the rest after they sit idle
)
```
