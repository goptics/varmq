## Try it

A worker with the default concurrency of 1 runs two jobs, one after the other. Press Run to run it in the Go Playground, or edit it first.

<GoPlay example="quick-start" />

## How it works

A worker owns your function and a concurrency limit. Each `Add` puts a job in a queue and returns at once. The worker's event loop hands waiting jobs to free goroutines, starts more while jobs wait, and lets them exit when the queue drains. [How it works](/concepts/how-it-works/) goes through it step by step.

![A varmq worker pool with concurrency 4: six Add calls produce one wake-up, the event loop dispatches four jobs to four goroutines, two jobs wait, and the pool shrinks back to one idle goroutine](../../../../assets/diagrams/varmq-worker-pool.svg)

## Performance

Measured on an i7-13700 (24 threads) on 2026-10-25. Charts, raw results and the harness are at [benchmarks.goptics.org](https://benchmarks.goptics.org).

<CardGrid>
	<Card title="4.89M tasks/s">
		Average over 15M tasks per run, 50K workers, 1 to 1M producers. The next fastest pool, a
		hand-rolled buffered channel pool, does 2.73M, and ants 2.22M. It uses more memory: 115 MB per 1M
		tasks against 15 MB for ants, because `Add` never blocks.
	</Card>
	<Card title="59,898 jobs/s on Redis">
		With redisq, one instance with 100 workers, moving 100K no-op jobs from 100 producers. The median
		time from enqueue to handler is 0.058 ms.
	</Card>
	<Card title="14,725 jobs/s on SQLite">
		With sqliteq, draining 20K jobs on WAL. goqite does 2,933 and River 3,230 on the same run.
	</Card>
</CardGrid>
