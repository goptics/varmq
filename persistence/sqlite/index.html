JOB 03Persistence and distribution

SQLite

sqliteq is the SQLite adapter for varmq. It keeps jobs in SQLite database files, so jobs survive a restart of the process with no server to run. It provides persistent queues only: it has no distributed queue, so WithDistributedQueue does not take it. Read persistence and distribution first for what a persistent queue does.

Setup

Section titled “Setup”

Three steps set it up:

  1. 1

    Add the two modules

    sqliteq uses mattn/go-sqlite3, which is built with cgo, so building needs CGO_ENABLED=1 and a C compiler.

    terminal
    go get github.com/goptics/varmq github.com/goptics/sqliteq
  2. 2

    Open the store

    sqliteq.New takes the path of a folder and returns a Queues value and an error. The folder is created if it does not exist.

    main.go
    sdb, err := sqliteq.New("data")
if err != nil {
	panic(err)
}
defer sdb.Close()
  3. 3

    Create a queue and bind it

    Each queue gets its own database file in the folder, named after the queue in lower case: the queue jobs lives in jobs.db. Both constructors take the name of the queue and return an error as well as the queue.

    main.go
    pq, err := sdb.NewQueue("jobs")
if err != nil {
	panic(err)
}
defer pq.Close()

queue := worker.WithPersistentQueue(pq)
    main.go
    pq, err := sdb.NewPriorityQueue("priority_jobs")
if err != nil {
	panic(err)
}
defer pq.Close()

queue := worker.WithPersistentPriorityQueue(pq)
queue.Add("alert", 1) // a lower number runs first

A queue name may only hold letters, digits, ., _ and -. The files use write-ahead logging.

To keep every queue in one file instead, pass WithSingleFile(): the path is then the database file, with one table for each queue. That is also how to open a file written by an older sqliteq, which kept every queue in one file. New returns an error when the path does not fit the layout, such as a file path without WithSingleFile().

Constructor Order Bind it with
NewQueue first in, first out WithPersistentQueue
NewPriorityQueue lowest number first WithPersistentPriorityQueue

Both take the name of the queue and return an error as well as the queue. Within one process, asking for the same name again returns the same queue. WithRemoveOnComplete(false) is an option for either. It keeps an acknowledged job in the table, marked as completed, where the default deletes it.

A persistent queue

Section titled “A persistent queue”

The program below binds a persistent queue to a worker with concurrency 1, adds ten jobs, and waits for them.

Three choices in it matter:

  • The worker is created with WithAutoRun(false) and started after the bind. Binding an sqliteq queue already makes the worker look for jobs a previous run left in the file, as the overview says. Starting it later only holds it back while the program counts them.
  • queue.Len() is read before Start. It counts the jobs in the table that are waiting, not the ones a worker has taken.
  • Every job finishes before the deferred closes run. WaitAndStop lets every job run, then stops the worker.

Jobs that were not acknowledged

Section titled “Jobs that were not acknowledged”

The overview describes when varmq acknowledges a job. This is what sqliteq does with a job that was taken and not acknowledged, for example because the process died.

The scene below shows the table of a queue named jobs. Take a job, then kill the process and restart the program. Or open the file from a second process while the job runs.

  • A job has a status in its row. A new row is pending. When the worker takes the job, one statement turns the row into processing. Acknowledge deletes the row, or marks it completed with WithRemoveOnComplete(false). It only matches a row that is processing.
  • Taken jobs return to pending when a queue is first opened. The first time a process opens a queue, with NewQueue or NewPriorityQueue, sqliteq sets every processing row that was not acknowledged back to pending. It does this once per queue in each process, and at no other time.
  • So a job from a crashed run comes back on the next start. The job that was running when the process died is processing in the file. The next program that creates the queue puts it back, and it runs again. There is no timeout. In the run above, that is the job you interrupted.
  • It also puts back jobs that are still running. sqliteq does not know which process took a row. Another process that opens a queue on the same file returns the first process’s running jobs to pending, and they run twice. To avoid that, use one process for each database file.
  • Len counts pending rows only. A job that is processing is counted by the worker’s NumProcessing, not by Len.

Other details

Section titled “Other details”
  • A worker takes several jobs in one statement. sqliteq implements IBatchAcknowledgeable, so a worker with only this queue claims as many jobs as it has free slots in one statement, and each one starts on its own goroutine at once.
  • Job IDs are checked. sqliteq implements IDedupQueue and IDedupPriorityQueue. An Add with WithJobId stores nothing while a row with that ID exists: pending, processing, or completed with WithRemoveOnComplete(false). Once the job is acknowledged and its row deleted, the ID can be added again.
  • Purge deletes every row. That includes the processing row of a job that is running. When the job finishes, its Acknowledge finds no row and returns false, and the worker reports ErrAcknowledgeJob to Errs() and the handler. The job’s function has run, so the error is about the bookkeeping.
  • There is no capacity. sqliteq does not implement CapacitySetter, so WithQueueCapacity does not make Add refuse jobs.
  • Close only stops the queue. It makes later Enqueue and Dequeue calls on that queue fail, for every holder of it in the process. It does not close the database. Close on the Queues value does.
