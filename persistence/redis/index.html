Redis

redisq is the Redis adapter for varmq. It provides first-in first-out and priority queues on one Redis server, each in a persistent and a distributed form. Read persistence and distribution first for what the two kinds of queue do.

Setup

Section titled “Setup”

redisq needs Redis 6.0 or newer, with Lua scripts allowed: it takes, adds and puts back jobs with scripts. Its go.mod asks for Go 1.26. The repository’s examples/compose.yml starts Redis 7.2 on port 6375, and the programs below use that port. From a clone of the repository:

Add the two modules to yours. varmq’s version is the release these pages describe:

redisq.New takes a Redis URL and returns a Queues value. It panics when the URL does not parse. Queues has one constructor for each kind of queue. Each takes a key, which names the queue in Redis:

Constructor Order Bind it with
NewQueue first in, first out, on a Redis list WithPersistentQueue
NewPriorityQueue lowest number first, on a sorted set WithPersistentPriorityQueue
NewDistributedQueue first in, first out, plus wake-ups for idle consumers WithDistributedQueue, or varmq.NewDistributedQueue with no worker
NewDistributedPriorityQueue lowest number first, plus wake-ups for idle consumers WithDistributedPriorityQueue, or varmq.NewDistributedPriorityQueue

A queue with the key jobs keeps its waiting jobs under jobs. It keeps the jobs a worker took and has not acknowledged under jobs:nacked, with their deadlines under jobs:timeouts and the heartbeats of the queue objects that took them under jobs:heartbeats. Its other keys, and a distributed queue’s wake-up channels, also start with jobs:.

Redis keeps these in memory. Whether they survive a restart of Redis itself is up to Redis’s own persistence settings, which neither varmq nor redisq changes.

A persistent queue

Section titled “A persistent queue”

The program below binds a persistent queue to a worker with concurrency 1, adds ten jobs, and waits for them.

Three choices in it matter:

  • The worker is created with WithAutoRun(false) and started after the bind. Binding a redisq queue already makes the worker look for jobs a previous run left in Redis, as the overview says. Starting it later only holds it back while the program counts them.
  • queue.Len() is read before Start. It asks Redis, so it counts the waiting jobs from the earlier run.
  • Every job finishes before the deferred closes run. WaitAndStop lets every job run, then stops the worker. A job acknowledges when its function returns. Close on a redisq queue puts back the jobs it took and has not acknowledged, so closing it under a running job sends that job back to the queue to run again, and the job’s acknowledgement fails.

A distributed queue

Section titled “A distributed queue”

A distributed queue is shared by any number of processes. The producer below has no worker. It wraps the Redis queue with varmq.NewDistributedQueue and adds jobs.

The consumer binds the same Redis queue to a worker with concurrency 5, and runs until you stop it.

How it fits together:

  • A job reaches one consumer. The consumer takes a job from the Redis list, and a job that has been taken is not in the list for another consumer. Two consumers on one key divide the jobs between them.
  • Add wakes an idle consumer. Enqueue on a distributed queue adds the job and, in the same step, wakes consumers that are waiting for work, up to one per waiting job, each on a channel of its own. A consumer waits for work once it finds the queue empty, and a busy one is not woken, so the wake-up goes to a consumer that can take the job. While jobs wait, every consumer also checks once a second, so a job added while no consumer was listening still gets picked up.
  • The producer has a Len and a Purge. On a distributed handle they are redisq’s own. Len is the length of the Redis list. Purge deletes the list, which removes every waiting job. A job that a consumer took and is running is not in the list, and Purge leaves it alone.
  • Each consumer’s counters are its own. Jobs run in one process and are added in another, so one instance’s Submitted and Completed need not match. These docs do not cover how a distributed queue’s counters count yet. The overview says what is known.
  • The consumer stops its worker before the deferred Close. Close puts back every job the consumer took and has not acknowledged, and wakes another consumer for them, so closing under a running job would run it twice. StopAndWait lets the running jobs finish and acknowledge first. redisq has a Listen method that blocks until SIGINT or SIGTERM. It does not stop the worker.

  3. In one terminal run go run ./consumer. It prints waiting in Redis: 0 and listening.

  4. For a second consumer, run go run ./consumer in another terminal. Each job goes to one of the two.

  5. In a third terminal run go run ./producer. It prints waiting in Redis: and a number. The number is 20 when no consumer is running, and lower when one has already taken some jobs.

  6. The consumers print a scraping line and, two seconds later, a scraped line for each job. Each consumer runs up to five jobs at a time, so five lines appear together.

  7. Press Ctrl+C in a consumer terminal. It finishes the jobs it is running, acknowledges them and exits.

To see a crash instead, run the producer again and kill one consumer with kill -9 while it runs jobs. The other consumer runs them a few seconds later, as the next section explains.

Jobs that were not acknowledged

Section titled “Jobs that were not acknowledged”

The overview describes when varmq acknowledges a job. This is what redisq does with a job that was taken and not acknowledged, for example because the process died.

  • A taken job is recorded in the same step. One script moves the job from the queue to the hash <key>:nacked, under its acknowledgement ID, and gives it a deadline in <key>:timeouts: Redis’s time plus the visibility timeout, five minutes by default. Acknowledge removes both entries.
  • Every queue object sweeps once a second. From its creation until Close, it puts back the jobs whose deadline has passed and the jobs held by a queue object taken for dead. On the first-in first-out queues they go to the front, and on a priority queue back at their priority. On a distributed queue the sweep wakes a consumer for them. Creating a queue object also puts back the jobs whose deadline has passed.
  • A queue object is taken for dead when its heartbeat runs out. Each one renews a heartbeat in <key>:heartbeats when it takes jobs and on every sweep, and the other queue objects on the key put back its jobs once the heartbeat is 30 seconds old, the default. Time in which no process swept the key does not count, because Redis cannot tell a dead process from a pause of all of them. A distributed consumer is taken for dead sooner: Redis drops its wake-up channel when its process exits, and five seconds later the other consumers put its jobs back.
  • So a job from a crashed run comes back. On a distributed queue, another consumer runs it about six seconds after the crash. On a persistent queue, it comes back once the program has been running again for 30 seconds, counted over all the runs since the crash, or as soon as a queue object finds it past its deadline, whichever comes first.
  • Close hands jobs back. Close puts back at once every job its queue object took and has not acknowledged. After it, Enqueue and Acknowledge on that object return false. Stop the worker before you close the queue.
  • The timeouts are set per queue object. SetVisibilityTimeout changes the deadline for jobs taken after the call. SetHeartbeatTimeout sets how long the object may go without reaching Redis: at least five seconds, and 0 turns heartbeats off. Call them right after you create the queue.
  • Keep the visibility timeout longer than your slowest job. A job still running past its deadline is put back by the next sweep and runs again.
  • Keep the heartbeat timeout longer than any freeze you want to ride out. A process that is frozen or cut off from Redis for longer is taken for dead. Its running jobs run again elsewhere, and their later Acknowledge still returns true.
  • GetNackedItemsCount counts the jobs in :nacked. The handle’s Len does not, because they have left the queue.

Job IDs

Section titled “Job IDs”

redisq implements IDedupQueue and IDedupPriorityQueue. An Add with WithJobId stores the job once per ID within a window, five minutes by default: another Add with the same ID in that time stores nothing, and still returns true. That covers an Add you retry, and a push that the Redis client sent again after its reply was lost. The ID is remembered for the whole window, even after its job has run. SetDedupWindow on the queue object changes the window, and 0 turns the check off.

A job without an ID is not checked. If the reply to its push is lost, the Redis client sends the push again, and the job can be stored twice. Give jobs IDs when that matters.

Batches

Section titled “Batches”

redisq implements IBatchAcknowledgeable, so a worker with only this queue takes as many jobs as it has free slots in one call, and each one starts on its own goroutine at once.
