Prometheus

VarMQ imports no metrics library. A worker exposes what Prometheus needs as plain methods: how many jobs are running and waiting, and four counters of what has happened. You wrap those methods in collectors from the Prometheus Go client. Its GaugeFunc and CounterFunc call a function each time Prometheus scrapes, so nothing of yours has to poll the worker.

The metrics

With the namespace foo_worker, each name starts with foo_worker_. The scene below replays the scrape of the program above. Move the clock, press a metric to read what it is, and see the PromQL for it. The numbers follow a real run of the program: 1000 jobs, 100 milliseconds each, 10 at a time.

NameTypeFromWhat it is
workers_processinggaugeNumProcessingjobs being processed right now
workers_concurrencygaugeNumConcurrencythe concurrency limit
workers_idlegaugeNumIdleWorkersidle goroutines in the pool
jobs_waitinggaugeNumPendingjobs that have not started. While a batch runs it can read high: see waiting
submitted_totalcounterSubmittedjobs the queue accepted
completed_totalcounterCompletedjobs whose function has returned
successful_totalcounterSuccessfuljobs that returned without an error or a panic
failed_totalcounterFailedjobs that returned an error or panicked

The four counters are the four of Metrics(). Metrics explains what each counts. Waiting explains what NumPending and NumProcessing count.

Queries to start with

These use the namespace foo_worker. Change it to the namespace you pass to each collector.

QuestionPromQL
How many jobs finish each second?rate(foo_worker_completed_total[5m])
What share of finished jobs fail?rate(foo_worker_failed_total[5m]) / rate(foo_worker_completed_total[5m])
How full is the pool? (1 means every slot runs a job)foo_worker_workers_processing / foo_worker_workers_concurrency
How large is the backlog?foo_worker_jobs_waiting
Do jobs arrive faster than they finish?rate(foo_worker_submitted_total[5m]) - rate(foo_worker_completed_total[5m])

The failure share is NaN while no job finishes. The pool can read above 1 just after TunePool lowers the limit, while the jobs already running finish. The last row is above 0 while jobs arrive faster than they finish. On a persistent queue it can mislead. Submitted counts only this process’s Add calls, so it does not count a job that another process added. Completed can then be higher than Submitted. On a distributed queue the counters may differ from what you expect. The overview says what each counter counts there.

What to watch for

  • The reads are not one snapshot. A scrape reads eight values at slightly different moments, and a job can finish between two of them. A set read while jobs run can be off by a few. Metrics says more.
  • The counters start at zero when the worker is created. They are totals. Use rate() or increase() in Prometheus to see how many jobs ran in a period. A restart of the process zeroes them, and Prometheus functions such as rate() read a drop as a counter reset.
  • Reset makes a counter fall. It zeroes the four counters, and Prometheus reads that as a reset, like a restart. Do not call it on a worker you export unless you want that.
  • One namespace for each worker. MustRegister panics when a collector with the same metric name is registered twice, with duplicate metrics collector registration attempted. Register each worker under its own namespace.
  • A worker on a persistent or distributed queue asks its storage. NumPending reads the length from Redis or SQLite. So every scrape makes that call. For the counters of such a worker, see the overview.

Prometheus scrapes /metrics by default, which is where the program serves them. If you serve VarMQ’s REST API as well, it can sit on the same server: mount it with http.Handle("/varmq/", varmq.Handler("/varmq")) next to the metrics route. The REST API lists only named workers, so give the worker a name. The REST API returns the same worker numbers as JSON, which suits a dashboard, and Prometheus suits history and alerts.
