JOB 01Operations

REST API

varmq ships an HTTP handler that lets you look at your workers and control them from outside the process. It serves JSON for a small set of routes, and it works on any worker that has a name.

Caution

The REST API has no authentication. Anyone who can reach it can stop your workers and change their concurrency. Before it is reachable from an untrusted network, protect it with middleware, network isolation or a reverse proxy.

Mounting it

Section titled “Mounting it”

Handler takes a path prefix and returns an http.Handler. It strips the prefix from each request before it looks for a route. Mount it on a mux with the prefix in the pattern, with a trailing slash:

You can also pass the handler to ListenAndServe itself, as examples/api-control does with varmq.Handler("/api"). Then the routes start at /api.

NewServerMux returns the same routes as an *http.ServeMux with no prefix, for mounting them yourself. Handler is NewServerMux behind that prefix, plus one more thing: it sets the instance header on every response, including the 404 and 405 replies the mux generates for itself. With NewServerMux alone, those two replies do not carry the header.

Which workers it serves

Section titled “Which workers it serves”

The API serves the workers in WorkerRegistry, a package-level sync.Map from name to worker.

  • Only a named worker is registered. WithName and a plain string argument to NewWorker both give a worker a name. A worker with no name is not in the registry and cannot be reached.
  • A worker is registered when it starts. A worker created with WithAutoRun(false) is not in the registry until you call Start.
  • A name holds one worker. Starting a second worker with the same name replaces the first in the registry, so the API reaches the second.
  • A stopped worker stays for a while. After it reaches Stopped, it is removed from the registry once WithStoppedRetention has passed, one minute by default, unless it was started again. Lifecycle has the details.
  • The order of /workers is not defined. It follows the order the map yields entries in.

You can read the registry yourself. varmq.WorkerRegistry.Load("email-sender") returns the worker as an any, and a type assertion to varmq.Worker gives you its methods, so you can build your own routes on it.

Routes

Section titled “Routes”
Method Path Does
GET /health returns {"status":"ok"}
GET /workers lists every registered worker, with a summary
GET /workers/{name} returns one worker, with its counters
PATCH /workers/{name}/actions/{action} pauses, resumes, restarts, starts or stops a worker
PATCH /workers/{name}/config/concurrency/{number} changes the worker’s concurrency limit

The {action} is one of pause, resume, restart, start and stop. Each calls the worker method of the same name, which lifecycle describes. Two behaviours follow from that:

  • pause and stop return at once. A worker that is running jobs reads Pausing or Stopping until they end. Read the worker again to see when it has changed.
  • restart waits. Restart stops the worker, waits until it has stopped, and starts it. The request is answered after that, so it can take as long as the running jobs do.

The concurrency route calls TunePool with the number. A number below 1 becomes the CPU count. Concurrency covers what a change does to jobs already running.

What a worker looks like

Section titled “What a worker looks like”

/workers returns a JSON array of these, and /workers/{name} returns one with a metrics object added:

Field From
name the worker’s Name
status Status: Initiated, Idle, Running, Pausing, Paused, Stopping or Stopped
concurrency NumConcurrency, the limit
num_processing NumProcessing
num_pending NumPending
num_idle_workers NumIdleWorkers
metrics.submitted, completed, successful, failed the four counters of Metrics()

Waiting covers what NumPending and NumProcessing count, and Metrics covers the four counters on in-memory queues. For a worker on a persistent or distributed queue, see the overview. These docs do not cover how a distributed queue’s counters count yet.

Responses

Section titled “Responses”

A response from one of these routes sets Content-Type: application/json, except a successful action, which has no body. An error is a JSON object with one field, error.

Status When Body
200 the request worked JSON for a read, empty for an action or a concurrency change
400 the action is not one of the five, or the concurrency is not a number {"error":"unknown action"} or {"error":"invalid concurrency value"}
404 no registered worker has that name {"error":"worker not found"}
409 the call returned ErrRunningWorker, ErrNotRunningWorker or ErrSameConcurrency the error’s message, for example {"error":"worker is already running"}
500 the call returned any other error the error’s message, for example {"error":"worker is stopped"}

The last two rows follow the error the worker returns. start on a worker that is running, and a concurrency change to the number it already has, are 409. A worker that is Pausing, Paused, Stopping or Stopped answers some calls with ErrWorkerPausing, ErrWorkerPaused, ErrWorkerStopping or ErrWorkerStopped, and those are 500. So resume on a worker that is Pausing is a 500 with worker is pausing, and so is pause on a stopped one. Errors lists which call returns which error.

Two replies do not come from the routes. A path the mux does not know is a plain-text 404 page not found, and a known path with the wrong method is a plain-text 405 Method Not Allowed with an Allow header.

Which instance answered

Section titled “Which instance answered”

InstanceHeader is the name of a response header, X-Varmq-Instance. Its value is InstanceID. When several instances sit behind one URL, such as a load balancer, the header tells you which process answered.

InstanceID is a package variable. It starts as the host name, which on Kubernetes is the pod name, or as an empty string if the host name is not available. Set it before you start serving when several instances share a host:

Every response from the routes carries the header, whether you use Handler or NewServerMux. As described above, only Handler also adds it to the mux’s own 404 and 405 replies.
