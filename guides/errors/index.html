JOB 11Worker pool guides

Errors

A failure in varmq shows up in one of three places, and a few values are returned directly from calls you make. This page covers where a failed job is reported, how to read the worker’s error channel and set an error handler, and every exported Err value with the call that returns it.

Add has no error result. It returns a bool, and false means the queue did not take the job. See queues.

Where a failure is reported

Section titled “Where a failure is reported”
Where What it gets Which workers
The job’s handle: Err() or Result() what the function returned, or the panic NewErrWorker and NewResultWorker
The worker’s Errs() channel every failure the worker sees all three
The error handler, set with WithErrHandler every failure the worker sees all three

A job’s function can fail in two ways, and both are reported the same way:

  • It returns an error. An error worker or result worker sends that error to the job’s handle, to Errs() and to the handler. The error is the same value you returned, so errors.Is works on it. A plain NewWorker function returns nothing, so it cannot fail this way.
  • It panics. The worker recovers the panic and counts the job as failed. The panic becomes an error, which goes where a returned error goes. A plain worker has no handle to carry it, so it goes to Errs() and the handler only.

The error for a panic reads panic recovered inside worker: <value>. For an error worker it is err-worker instead of worker, and for a result worker result-worker. The value is formatted into the text with %v, so errors.Is cannot find the panic value inside it. Worker types shows the three handles side by side.

The worker itself can also report an error that belongs to no job function: a storage problem or a failed acknowledgement. Those go to Errs() and the handler only.

For a group of jobs added with AddAll, an error group handle has its own Errs(). That one is a different channel, and it is closed once the group has ended. The worker’s Errs() below is not. See adding many jobs. A failure in a group job also reaches the worker’s Errs() and the handler.

The Errs channel

Section titled “The Errs channel”

The worker’s Errs() returns a read-only channel of error. Three things to know about it:

  • It holds one error. The channel has room for a single value. When a job fails and the channel is full, the error is not put on the channel, and the worker does not wait for you. A reader that is slow, or absent, loses errors. The handler does not.
  • It is never closed. for err := range worker.Errs() does not end when the worker stops, so run it in a goroutine of its own, or read with select and a default.
  • An error does not say which job it came from. Put the job’s ID or something that identifies the work in the message you return.

A reader like this one drains the channel as errors arrive. If you need every error, set a handler as well: the channel can still drop an error when two arrive faster than the reader takes them.

The error handler
Section titled “The error handler”


WithErrHandler sets a function that the worker calls for every error it reports. The function receives the Worker and the error, so one handler can serve several workers and log the worker’s Name().   • The handler runs for every error, including those the full Errs() channel dropped.
    • 

  • It runs synchronously on the goroutine that reports the error, and it must not block. For an error from a job, or from a failed acknowledgement, that is the goroutine that ran the job, so a slow handler delays that goroutine’s next job. For an error from pulling a job off its storage, it is the worker’s event loop, which hands out every job, so a slow handler holds them all back.
    • 

  • Passing nil is ignored. The worker keeps the handler it had.
    • 

  • The default handler does nothing. DefaultErrHandler changes it for the workers you create after the call. Configuration says how the defaults work.

Sent to Errs and the handler
Section titled “Sent to Errs and the handler”


These four are not returned from any call. The worker reports them when it pulls a job from its storage or closes a finished job. They go to Errs() and to the handler, and the worker carries on.






Error
Message
Reported when






ErrFailedToDequeue
failed to dequeue job
A bound queue’s Dequeue returned no job at the moment the worker pulled from it. The worker checks that a queue is not empty before it pulls, so the built-in queues rarely give it.




ErrFailedToCastJob
failed to cast job
The storage returned something that is not a job of the worker’s type. The built-in queues hold jobs, so this comes from custom, persistent or distributed storage.




ErrParseJob
failed to parse job, followed by the decoder’s message
A persistent or distributed queue returned bytes that do not decode as a job. The error wraps ErrParseJob, so match it with errors.Is.




ErrAcknowledgeJob
queue failed to acknowledge job, followed by the job and acknowledgement IDs
A persistent or distributed queue refused the acknowledgement when the worker closed a job it had taken from it. The error wraps ErrAcknowledgeJob.






Only persistent and distributed storage hands out bytes to decode or jobs to acknowledge, so ErrParseJob and ErrAcknowledgeJob do not come from the built-in in-memory queues. Persistence covers those queues.


One more error has no variable. The helpers Func, ErrFunc and ResultFunc handle a nil function with the error provided function is nil. ErrFunc and ResultFunc return it; Func panics with it, so the text arrives inside the panic message. It is not exported, so match it with strings.Contains. See function helpers.
