JOB 06Guides

Adding many jobs

AddAll queues a slice of Item values in one call. It returns one handle for the whole group, not one per job. It is a method of the in-memory queues: persistent and distributed queues have only Add.

An Item has three fields:

FieldMeaning
DataWhat you would pass to Add.
IDAn optional job ID. The worker sees it with a g: prefix. Job IDs has the rules.
PriorityRead by a priority queue only. A FIFO queue ignores it. A lower number runs first, as in queues.

The group handle

The handle’s type follows the worker, as it does for Add. Worker types compares the three.

WorkerAddAll returnsWhat you read
NewWorkerEnqueuedGroupJobnothing, you only wait
NewErrWorkerEnqueuedErrGroupJobErrs()
NewResultWorkerEnqueuedResultGroupJob[R]Results()

All three have NumPending() and Wait(). The error and result handles also have Drain().

  • NumPending is the number of jobs in the group that have not ended. A job ends when it runs, or when it is closed without running, by Purge for example. The number counts down to 0.
  • Wait blocks until NumPending is 0. On a plain worker, group.Wait() is all you need.

There is no Close on a group handle, and no status for a single item. To close one job, add it with Add instead, which gives you a handle of its own.

Items the queue refuses

The scene shows the same items added both ways. Add the items, then start the worker.

AddAll adds the items one at a time. It skips each item the queue does not take:

  • the queue is full or closed;
  • the item’s ID belongs to a job still in the queue;
  • the item’s ID repeats an earlier item in the same slice, and the first copy is still in the queue. A running worker may already have taken it.

A skipped item never runs and sends nothing to Results() or Errs(). It does not count in NumPending, so NumPending can start below len(items).

AddAll does not say which items it skipped. If you need to know, call Add for each job: it returns a bool per job.

The worker below is created with WithAutoRun(false), so you can look at the group before any job runs. The third item repeats the ID a.

adding-many-skipped/main.go
8 lines: package and imports
package main

import (
	"fmt"

	"github.com/goptics/varmq"
)

func main() {
	// Not started yet, so we can look at the group before any job runs.
	worker := varmq.NewWorker(
		func(j varmq.Job[string]) {
			fmt.Println("running", j.ID(), j.Data())
		},
		varmq.WithAutoRun(false),
	)
	queue := worker.BindQueue()

	items := []varmq.Item[string]{
		{ID: "a", Data: "resize"},
		{ID: "b", Data: "upload"},
		{ID: "a", Data: "resize again"}, // "a" is still in the queue: skipped
	}
	group := queue.AddAll(items)
	fmt.Println("pending:", group.NumPending(), "of", len(items))

	worker.Start()
	group.Wait()
	fmt.Println("pending:", group.NumPending())
}

Output



pending: 2 of 3 shows the repeat was skipped. After Start, only g:a and g:b run, Wait returns, and NumPending is 0.


Reading results


Results() returns a channel of Result[R] values. It returns at once. Ranging over the channel is what waits.


adding-many-results/main.go
9 lines: package and imports
package main

import (
	"fmt"
	"strconv"

	"github.com/goptics/varmq"
)

func main() {
	worker := varmq.NewResultWorker(func(j varmq.Job[string]) (int, error) {
		return strconv.Atoi(j.Data())
	}, 3)
	queue := worker.BindQueue()

	group := queue.AddAll([]varmq.Item[string]{
		{ID: "a", Data: "10"},
		{ID: "b", Data: "x"},
		{ID: "c", Data: "30"},
	})

	for r := range group.Results() {
		if r.Err != nil {
			fmt.Println(r.JobId, "failed:", r.Err)
			continue
		}
		fmt.Println(r.JobId, "=", r.Data)
	}
	fmt.Println("pending:", group.NumPending())
}

Tab inserts a tab. Esc leaves the editor. Ctrl+Enter runs.
Output


The worker has concurrency 3, so the three result lines can come in a different order on each run. g:b fails to parse and arrives as an Err. pending: 0 prints after the loop ends by itself.


    

  • A Result has a JobId, a Data value and an Err. A job that succeeded has Data. One that failed has Err, and Data is the zero value. A panic arrives as an Err.
    • 

  • JobId is the item’s ID with the g: prefix. It is empty for an item with no ID, unless the worker has a job ID generator.
    • 

  • Results arrive in the order the jobs finish. With concurrency above 1 that is not the order of your slice, so match results to items by JobId. With concurrency 1 on a FIFO queue they come back in the order you added them.
    • 

  • A job closed before it ran sends nothing.
    • 

  • The channel closes once every job in the group has ended, so the range loop finishes by itself. For an empty slice, the channel is closed when AddAll returns, so the loop ends at once. In v1.10.0 it never closed, and the loop never finished.
    • 

  • The channel has room for one value per item. A slow reader does not delay the workers.
    • 



Reading errors


Errs() returns a channel of error. It carries failures only: a job that succeeded sends nothing, so the number of values you receive is the number of jobs that failed. A panic counts as a failure. The channel closes once every job has ended, so ranging over it finishes by itself. For an empty slice it is closed at once, as for Results().


An error does not say which job it came from. If you need that, put the job’s ID in the message, as the worker function below does with j.ID().


adding-many-errors/main.go
8 lines: package and imports
package main

import (
	"fmt"

	"github.com/goptics/varmq"
)

func main() {
	worker := varmq.NewErrWorker(func(j varmq.Job[int]) error {
		if j.Data() < 0 {
			// An error does not name its job, so put the ID in the message.
			return fmt.Errorf("%s: %d is negative", j.ID(), j.Data())
		}
		return nil
	})
	queue := worker.BindQueue()

	group := queue.AddAll([]varmq.Item[int]{
		{ID: "p", Data: 5},
		{ID: "q", Data: -1},
		{ID: "r", Data: 7},
		{ID: "s", Data: -2},
	})

	failed := 0
	for err := range group.Errs() {
		fmt.Println(err)
		failed++
	}
	fmt.Println(failed, "of 4 failed")
}

Tab inserts a tab. Esc leaves the editor. Ctrl+Enter runs.
Output


Two of the four items are negative, so the loop receives two errors, g:q and g:s. The jobs that succeeded sent nothing.


If you do not read the channel


Drain() discards the results or errors the channel still holds, for a caller that is not going to read them.
