Concurrency

A worker’s concurrency is the most jobs it runs at the same time. This page covers how to set it, how to change it while the worker runs, and the options that decide how many idle goroutines the worker keeps. How it works shows the pool behind it.

Setting the limit

Section titled “Setting the limit”

The default is 1. A plain int after the worker function sets it, WithConcurrency sets it as an option, and DefaultConcurrency changes the default for workers created after the call:

If you pass more than one value to a worker, the last one wins. Worker types lists the other arguments that NewWorker takes.

A value below 1 means one per logical CPU. 0 and -1 both become runtime.NumCPU(), so the number depends on the machine. The same rule applies to DefaultConcurrency and to TunePool, below.

A limit, not a pool size

Section titled “A limit, not a pool size”

NumConcurrency() returns the limit. It is an upper bound on the jobs running at once, not a number of goroutines the worker creates. The worker starts a goroutine when jobs are waiting and one more would clear the backlog faster than it costs to start it, up to the limit, and goroutines exit when the backlog is gone. A worker with a limit of 100 and three waiting jobs does not start 100 goroutines. How it works has the details.

Four methods on Worker report what the pool is doing:

Method Returns
NumConcurrency the limit
NumProcessing the jobs running right now, counted as busy goroutines
NumPending the jobs that have not started: waiting in a queue, in a batch a goroutine took, or parked by a pause or stop. While a batch runs it can read high: see waiting
NumIdleWorkers the idle goroutines waiting in the pool for a job

NumProcessing stays at or below the limit, except for a while after TunePool lowers the limit. All four are snapshots: they can change right after you read them.

Changing the limit with TunePool
Section titled “Changing the limit with TunePool”


TunePool changes the limit of an active worker, one that is Idle or Running. It returns at once, and the new limit applies to the next job the worker hands out. A value below 1 means one per CPU, as above.




It returns an error in two cases:


    

  • ErrSameConcurrency: the worker already has that limit.
    • 

  • The worker is not Idle or Running. TunePool only works on an active worker, so it returns the error for the worker’s state: ErrNotRunningWorker before Start, ErrWorkerPausing or ErrWorkerPaused while pausing or paused, and ErrWorkerStopping or ErrWorkerStopped while stopping or stopped. Raising the limit
Section titled “Raising the limit”


The worker starts jobs on new goroutines as soon as it can. That covers the jobs still in a queue and the jobs you add later.


A job a goroutine has already taken into a batch stays with that goroutine, which runs its batch one job after another. This matters most at concurrency 1, where one goroutine can take up to 32 jobs at once from an in-memory FIFO queue: raising the limit does not spread out jobs it already holds. Lowering the limit
Section titled “Lowering the limit”


Nothing running is interrupted. The worker hands out no new batch until fewer goroutines are busy than the new limit, so NumProcessing can stay above NumConcurrency until those goroutines finish their batches. A goroutine that already holds a batch keeps running it one job after another, so jobs from batches already handed out still start after the change. The worker removes idle goroutines it no longer needs at once, unless you set an expiry duration, in which case the expiry removes them (see below).


Idle goroutines
Section titled “Idle goroutines”


A worker with default settings keeps one idle goroutine in its pool. A goroutine that finishes a job stays in the pool if more jobs are waiting than idle goroutines are ready to run them, or if the pool holds fewer idle goroutines than the minimum, which is one. Otherwise it exits. Two options change this.


WithMinIdleWorkerRatio sets the share of the limit to keep idle, as a percentage from 1 to 100. The worker keeps limit * percentage / 100 idle goroutines, rounded down, with a floor of one. With a limit of 4, a ratio of 50 keeps 2 and a ratio of 100 keeps 4. A value outside the range is clamped: 0 becomes 1 and anything above 100 becomes 100. The limit here is the current one, so the minimum follows a TunePool.


WithIdleWorkerExpiryDuration makes the pool shrink on a timer instead. With it set, a goroutine that finishes a job goes back to the pool instead of exiting. Once per duration the worker removes the goroutines that have been idle for longer than the duration, down to the minimum above. Because the check runs once per duration, a goroutine can sit idle for up to about twice the duration before it goes. Without the option there is no timer, and the pool shrinks as goroutines finish.




Idle goroutines let the next burst of jobs start without paying to start goroutines. Each one holds a goroutine’s memory. DefaultMinIdleWorkerRatio and DefaultIdleWorkerExpiryDuration set both for workers created after the call. Configuration lists every option and its default.
