Function helpers

A worker usually knows what its data means: a string is an email address, an int is a user ID, and the worker function knows what to do with it. When you only want to run pieces of code on a pool, the data can be a function instead. Func, ErrFunc and ResultFunc each return a ready-made worker function that calls the job’s function.

Helper Use it with The job’s data is Add returns
Func() NewWorker func() EnqueuedJob
ErrFunc() NewErrWorker func() error EnqueuedErrJob
ResultFunc[R]() NewResultWorker func() (R, error) EnqueuedResultJob[R]

You pass what the helper returns, so you call it:

Go works out the data type from the helper, so there is nothing to spell out for Func and ErrFunc. ResultFunc returns a function for any result type, so you name it yourself: varmq.ResultFunc[string](). Worker types covers what each handle gives back.

Details
Section titled “Details”


A nil function. Each helper handles nil in its own way:


    

  • Func panics. The worker recovers it, so the program carries on, and the panic goes to the worker’s Errs() channel, because a plain handle has no place for it.
    • 

  • ErrFunc returns an error, which you get from Err().
    • 

  • ResultFunc returns the zero value and an error, which you get from Result().
    • 



Panics. A panic inside your function is handled like a panic in any worker function. Worker types says where each kind reports it.


Closures run later. A function runs on a worker goroutine, not on the goroutine that called Add. Anything it captures has to be safe to share. Changing a captured variable after Add is a data race unless you synchronise the access.


No persistence. A persistent or distributed queue stores each job as JSON, and a function cannot be encoded as JSON. Keep function jobs for in-memory queues. For jobs that must survive a restart, use plain data and put the logic in the worker function.


Naming jobs. The job’s Data() is the function, so nothing about the job says what it does. WithJobId gives it a name. See job IDs.
