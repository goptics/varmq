JOB 08Worker pool guides

Topics

A queue gives each job to one worker. A Topic gives each payload to every worker subscribed to it. Use one when several workers must each act on the same event, such as sending an email and updating stock for the same order.

In-memory queue Topic
Who gets a job one worker, once every subscribed worker, each with its own job
You send with queue.Add(x) topic.Publish(x)
You get back a job handle and a bool a bool

Topics are in-memory only. A topic lives in your process. Nothing is written to disk, and a payload is lost when the process exits.

WithTopic is available on the worker that NewWorker returns. Error and result workers cannot subscribe: see the table in worker types.


WithTopic returns a Subscription, the worker’s handle on the topic. A subscription has no Add, because the topic is the only producer. Two calls panic: subscribing a worker to a topic it is already subscribed to, and passing a nil topic. A worker can subscribe again after it unsubscribes.


Publishing
Section titled “Publishing”


Publish stores the payload once and wakes every subscribed worker. Each worker then makes its own job from the payload. The payload is copied by value, so if T is a pointer or holds pointers, maps or slices, every subscriber shares what they point to.


Publish returns true once the payload is stored. It returns false, and no subscriber gets the payload, in three cases:


    

  • no worker is subscribed, so the payload has nowhere to go;
    • 

  • the topic is closed;
    • 

  • the topic is full: see capacity.
    • 



It returns when the payload is stored, not when the jobs finish. To wait for a subscriber’s jobs, wait on that subscriber’s worker: waiting covers how. A job made from a payload gets its ID from the subscriber’s own job ID generator, and a worker with no generator gives it none.


A worker receives only the payloads published after it subscribed. A payload that Publish refused for lack of subscribers is not kept for the next one.

How a topic stores payloads
Section titled “How a topic stores payloads”


A topic keeps one copy of each payload in a shared in-memory log, however many workers subscribe. Each subscription reads the log at its own position, so a slow worker does not block Publish or the other workers. A payload is freed once every subscription has read it. In the diagram, that is why a chunk of the log stays while the slower worker’s cursor is still on it.


The same rule means a subscriber that is slow, paused or stopped holds on to every payload published since it fell behind, until it catches up, purges or unsubscribes. For a worker that may stall, set a capacity.


Unsubscribing
Section titled “Unsubscribing”


Unsubscribe on the subscription ends it. The worker gets nothing more from the topic, and the payloads it has not read yet are dropped. A job the worker has already taken from the topic is not recalled: a running job finishes, and a job waiting in a batch still runs. Calling it twice is safe. Close on the subscription does the same.


Purge on a subscription keeps the subscription and drops the unread payloads. Unlike Unsubscribe, it also discards the jobs the worker has taken from the topic but not started, so a job waiting in a batch does not run. A job that is already running finishes. Purge does not call Close on the payloads. Len is the number of payloads the subscription has not read, and Worker() returns its worker.


To end every subscription at once, call Close on the topic. It unsubscribes all of them, and every later Publish returns false. NumSubscribers() tells you how many are attached.

Capacity
Section titled “Capacity”


A topic has no limit unless you set one. WithTopicCapacity bounds it when you create it.


The limit applies to the slowest subscription. Once it has that many payloads unread, Publish returns false, the way Add does on a full queue, and the refused payload reaches no subscriber. Room comes back as that subscription reads, purges or unsubscribes. A value below 1 means no limit.


Tab inserts a tab. Esc leaves the editor. Ctrl+Enter runs.


The worker is created with WithAutoRun(false), so it reads nothing until Start. Two payloads fit, and the third is refused while 2 are unread. Once the worker has read both, there is room, and the same Publish succeeds.


IsFull() on the topic tells you whether it is at its capacity right now, and the answer can change straight after. On a subscription, IsFull() is true when that subscription is at the capacity, which makes it the one refusing Publish. Act on the result of Publish itself, not on IsFull.


Priority and strategy
Section titled “Priority and strategy”


A topic subscription is one more source of its worker, next to any queues bound to it. The worker’s strategy picks which source gives the next job. WithTopicPriority ranks the subscription the way WithQueuePriority ranks a queue: a lower number goes first, and without it the subscription ranks last.




With the default Priority strategy, a worker with a topic subscription ranked 1 and a queue without a rank takes the payloads first. If the two have the same rank, the one bound first goes first. Strategies covers what priority does under the other three.


A worker whose only source is a topic takes payloads in batches, like a worker with one in-memory FIFO queue. With more than one source it takes one job at a time. How it works has both.
